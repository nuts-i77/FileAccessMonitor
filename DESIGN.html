アーキテクチャ概要

FileAccessMonitor は Windows サービスとして動作し、Windows セキュリティイベントログからファイルアクセス（読取・書込・削除・名前変更）を収集して、REST API と SPA の Web GUI で可視化するツールです。1 台で完結する構成のほか、複数のファイルサーバーにエージェントを置き、1 台の監視サーバーに記録を集める構成をとれます。

[ファイルサーバー A]                [ファイルサーバー B]
  エージェント                        エージェント
  Security ログ → 収集 → 送信待ち     （同じ）
  名前変更/フォルダ判定・SACL・
  フォルダ一覧（指示に応じて）
        │ HTTPS :8443（エージェントから接続、証明書は指紋で固定）
        ▼
[監視サーバー]（1 台構成ではこれだけ）
  Security ログ → 収集（自分自身の分）
  SQLite（記録・ユーザー・エージェント・操作ログ）
  ASP.NET Core REST API + SPA（http :8080）
  通知（Webhook / メール）・エージェントの無応答検知
        ▲
        │ JWT Bearer
     ブラウザ（管理者のブラウザは GitHub に最新版を問い合わせる）
前提：SACL の適用と Security ログの読み取りはローカルでしかできないため、収集は各ファイルサーバー上で行います（1 台構成では監視サーバー自身、複数台ではエージェント）。通信は常にエージェントから監視サーバーへ向かい、監視サーバーからファイルサーバーへは接続しません。

構成と役割

同じプログラム（FileAccessMonitor.csproj、net10.0。win-x64 と linux-x64 で発行）が、起動時の状態によって役割を変えます。Windows ではインストーラーで、Linux では linux-server/install.sh のオプションで役割を選びます。Windows 専用の部分（イベントログ、SACL、DPAPI、証明書ストア）は [SupportedOSPlatform("windows")] を付け、実行時に OS で切り替えます。

役割判定動くもの
1 台構成 / 監視サーバーagent.json がないローカル収集（LocalRecordSink。Windows は EventLogCollectorService、Linux は SambaAuditCollector）、Web GUI と API、DB、通知、エージェント用ポート、エージェント監視
監視サーバーのみ上記で settings.json の "LocalCollection": falseローカル収集なし（監査ポリシーや SACL、smb.conf にも触れない）。サーバーの一覧に自分自身を出さない（ServerConfigService.LocalCollects）。起動時に読むので、切り替えは再起動で反映
エージェント%ProgramData%\FileAccessMonitor\agent.json がある収集（RemoteRecordSink）、送信（AgentSender）、指示の実行（AgentJobRunner）。Web GUI と DB はない（AgentHost.RunAsync）
Linux エージェント別の実行ファイル fileaccessmonitor-agent（linux-agent/）Samba の監査ログの収集（SambaAuditCollector）、送信と指示の実行（Windows 版と共通）。Linux エージェントを参照

コマンドライン

FileAccessMonitor.exe enroll <接続文字列>   # 監視サーバーに登録して agent.json を作る（インストーラーも使用）
FileAccessMonitor.exe unenroll               # agent.json を消して 1 台構成に戻す
FileAccessMonitor.exe local-collection off   # 監視サーバーのみにする（on で戻す。インストーラーも使用）

データフォルダは既定で C:\ProgramData\FileAccessMonitor（Linux は /var/lib/fileaccessmonitor）。環境変数 FILEACCESSMONITOR_DATA で別のフォルダを指定でき（AppPaths.DataDir）、インストール済みの環境に影響を与えずに開発用・デモ用のインスタンスを動かせます。

イベント処理パイプライン

EventLogCollectorService が次の XPath で Security ログを購読します（1 台構成・監視サーバー・エージェント共通）。

*[System[(EventID=4663) or (EventID=4659) or (EventID=4660) or (EventID=4670)
  or (EventID=4656 and band(Keywords,4503599627370496)) or (EventID=4624) or (EventID=5140)]]

4503599627370496 は 0x10000000000000（Audit Failure）。成功の 4656 は読まないので、既存の成功監査による負荷は増えない。

イベント ID内容処理
4663オブジェクトへのアクセスAccessMask から種別を判定。削除権限を含むものは DeleteTracker で保留
4659削除目的のハンドル要求常に Delete
4660オブジェクトの削除同じ (ProcessId, HandleId) の保留中アクセスを Delete と確定
4656（失敗）オブジェクトのハンドル要求が拒否された（Audit Failure）要求マスクから種別を判定して Denied の記録（下記）
4670オブジェクトの権限の変更OldSd / NewSd（SDDL）の差から Permission の記録（下記）
4624ログオンログオン ID → (IP, 端末名) をキャッシュ
5140共有へのアクセスログオン ID → IP をキャッシュ
1102監査ログの消去ログ消去を検知したとき、消去したユーザーを調べるためだけに参照

流れ

EventLogWatcher（ブックマークから再開）
  → Channel<RawEvent>（XML をここで解析して EventRecord を手放す）
  → 単一のコンシューマー: ProcessEvent → DeleteTracker / ReadMerger
  → 最大 500 件ずつ IRecordSink.SaveAsync(records, lastRecordId)
       LocalRecordSink : 記録と読み取り位置を 1 トランザクションで DB に保存 → AlertService.Observe
       RemoteRecordSink: 送信待ちフォルダに書いてから読み取り位置を保存（AgentSender が送る）

記録がない間も、読み取り位置は 5 秒ごとに保存します。保存に 3 回失敗したバッチは破棄してログに残します。

停止中の取りこぼし対策

  • 前回の読み取り位置（RecordId）のブックマークから readExistingEvents で読み直す
  • RecordId が巻き戻っていればログが消去されたと判断し、ログ全体を読み直して「記録の途切れ」（ログ消去、消去したユーザー付き）を報告
  • 前回の位置がすでに上書きされていれば、残っている範囲を読み、欠けた範囲を「記録の途切れ」として報告
  • 報告は IRecordSink.ReportGapAsync 経由。操作ログ collector.gap と通知（エージェントの分は監視サーバーで処理）

AccessMask の判定

0x10000 (DELETE)                         → Delete 候補（DeleteTracker で確定）
0x2 / 0x4 / 0x40000000 (WriteData など)   → Write
0x1 / 0x80000000 (ReadData など)          → Read
その他（属性・EA の読み書きなど）          → 記録しない

フィルタの順番（ProcessEvent）

  1. 削除権限を含む 4663 は、まず同じハンドルの保留を解除（DeleteTracker.Release）。除外される記録でも行う
  2. NT デバイスパスをドライブレターに変換し、代替データストリーム（file:stream）を除外
  3. 監視フォルダの配下か（監視フォルダが未設定なら全体）
  4. システムアカウント（xxx$, SYSTEM など）と ExcludeProcessNames（appsettings）
  5. 記録ルールの除外（ファイル名・ユーザー・プロセス）
  6. フォルダごとの記録種別（名前変更は「削除」の設定に従う）
  7. フォルダへのアクセスは、削除権限のもの以外は除外
  8. 連続した読取のまとめ（ReadMerger）。拒否の記録は別の DeniedMerger（ユーザー・パス・種別ごとに 60 秒、ReadMerger と混ぜない）

権限の変更（4670）と拒否（4656 失敗）も同じフィルタ（監視フォルダ、システムアカウント・除外、記録ルール、フォルダごとの記録種別）を通ります。ただし拒否はフォルダも記録し（入れないフォルダの一覧表示など）、DeleteTracker や 4660 は使わず、拒否された削除は Delete + Denied としてすぐ記録します（拒否された名前変更も Delete + Denied。区別できない）。

接続元 IP / 端末名

ログオン ID → (IP, 端末名) のキャッシュ（起動時に過去 30 日分の 4624/5140 を先読み）と、NetSessionEnum で 30 秒ごとに更新する SMB セッション一覧（ユーザー名 → IP）を使います。端末名が分からなければ、逆引き DNS サーバーが設定されている場合だけ DnsResolverService で PTR を引きます（成功 1 時間・失敗 5 分キャッシュ）。逆引き DNS は監視サーバーの設定だけで、エージェントの記録は監視サーバーが受け取ったときに解決します（エージェントでは引かない）。

削除・名前変更・フォルダの判定

名前変更・移動でも、ファイルは削除権限（0x10000）で開かれます。違いは、実際に削除されたときだけ同じハンドルの 4660 が続くことです。DeleteTracker は削除権限のアクセスを (ProcessId, HandleId) ごとに最大 2 秒保留して判定します。

状況記録
同じハンドルの 4660 が来たDelete
4660 が来ず、元のパスに何もないRename（名前変更・移動）
4660 が来ず、元のパスにファイルがある削除以外の権限の種別、なければ Write（Office の保存は、旧ファイルを別名にして新ファイルを元の名前にするため）
4660 が来ず、元のパスにフォルダがある記録しない（削除権限で開いただけ）
同じハンドルで新しい削除権限のアクセス前の保留は「削除ではない」として上記で確定（ハンドル番号の再利用対策）

保留の期限は、新しいイベントの時刻（停止中の分を読み直しているとき）か実時間のどちらかで 2 秒を過ぎたときです。キューが空でも保留があれば、待機を 2 秒で切り上げて判定します。

名前変更の移動先（NewPath）と、書込が作成だったか（Create）は、Security ログにないため USN ジャーナルから補います（次の「拒否・権限変更・作成・USN」）。DeleteTracker が判定した後の Write と Rename が、突き合わせのために少しだけ保留されます。

フォルダの判定

イベントにはファイルかフォルダかの区別がないため、処理時点で Directory.Exists を確認し、さらに最近見たフォルダ（記録の親フォルダ、存在したフォルダ）を RecentFolders に覚えておきます。フォルダを削除すると中身が先に削除されるので、フォルダ自体が消えていても判定できます。空のフォルダで処理時点にすでに消えているものは判定できず、ファイルとして記録されます。

記録ルール

サーバーごとの settings.json の Recording キー（RecordingSettings）。キーがなければ既定値を使います。エージェントのサーバーの分は監視サーバーで管理し、エージェントに配布します。

ExcludeFilePatternsファイル名のパターン（* ?、大文字小文字を区別しない）。既定 Thumbs.db, desktop.ini, ~$*, *.tmp
ExcludeUsersDOMAIN\user、またはユーザー名のみ（全ドメインに一致）
ExcludeProcessesプロセス名。共有経由のアクセスにはプロセス名がないため、サーバー上で開いたものにだけ効く
RecordDenied既定 true。拒否されたアクセスも記録する（Linux は再適用でエージェントの full_audit:failure が変わる）
MergeReadMinutes既定 5。同じユーザー・同じファイルの読取は、前回の読取からこの時間内なら記録しない（時間は読取のたびに数え直す。0 = すべて記録）

設定の変更は、settings.json の更新日時を 1 秒ごとに確認して反映します（監視フォルダも同じ）。記録済みのデータには影響しません。

エージェント用ポート

  • HTTPS、既定 8443（Agents:Port）。Kestrel に ListenAnyIP で追加
  • 1 台構成 / 監視サーバーでは常に待ち受ける（エージェントを登録するときに再起動が要らないように）。ファイルサーバーから届くかはファイアウォールで決まる。settings.json の "Agents": { "Enabled": false } で開かない（AgentEndpoint.Enabled）。ポートの変更は "Agents": { "Port": n } と再起動。登録済みのエージェントは再登録が必要
  • 証明書は自己署名（CN=FileAccessMonitor Agent Endpoint、RSA 2048、有効期限 20 年）。初回に作成して LocalMachine\My に保存。エージェントは SHA-256 の指紋で固定するため認証局は不要
  • このポートでは /api/agent/* だけを受け付け、/api/agent/* はこのポートでしか受け付けない（ミドルウェアで 404）

登録と送信

登録

  1. 管理者が登録コードを発行（24 時間有効・1 回限り。DB には SHA-256 のハッシュだけを保存）
  2. 接続文字列 FAM1. + base64url({"u": URL, "f": 証明書の指紋, "c": コード}) を作る。URL は GUI で書き換えて作り直せる
  3. エージェントが enroll で POST /api/agent/enroll。成功すると エージェントID.秘密 のキーを受け取り、agent.json（SYSTEM / Administrators のみ読み取り可）に保存
  4. 同じサーバー名で登録し直すと、キーを入れ替えて通し番号をリセット（記録は同じ名前のまま続く）

送信（AgentSender）

  • 収集した記録は、まず送信待ちフォルダ outbox\ に通し番号のファイルとして書く（最大 2 GB）。読み取り位置は agent-position.txt
  • 古い順に POST /api/agent/batch。成功したら削除。失敗したら 5 秒から最大 5 分まで間隔を広げて再試行。401 のときは 5 分待つ（無効化・削除されたエージェント）
  • 監視サーバーは通し番号を確認し、保存済みの番号なら保存せずに成功を返す（応答が失われた再送を二重に保存しない）。記録と番号は 1 トランザクション
  • 送るものがないときは 1 分ごとに heartbeat（バージョン、送信待ち件数、監査が有効か、OS 名。Linux で監視フォルダがないときの監査は null で、一覧では「-」）。バッチ送信時も X-Agent-Outbox ヘッダーで残り件数を伝える
  • 記録の途切れの報告も、送信待ちフォルダ経由で同じ順番で送る
  • 接続元の端末名は、エージェントがログオンイベントから分かった場合だけ付けて送る。分からない記録は、監視サーバーが受け取ったときに自分の逆引き DNS 設定で解決する（IP ごとに 1 回、キャッシュあり）。DNS の設定と経路は監視サーバーだけで済む

設定の配布と指示

設定の配布

エージェントのサーバーの監視フォルダと記録ルールは、監視サーバーの Agents.Config（settings.json と同じ形の JSON）に保存し、変更のたびに ConfigVersion を上げます（ServerConfigService）。エージェントは heartbeat の応答で版の違いを知ると GET /api/agent/config で取得し、自分の settings.json の MonitoredPaths と Recording を書き換えます。収集側は既存のファイル監視でそのまま反映します。逆引き DNS は配布しません（下記のとおり監視サーバーで解決するため）。

指示（ジョブ）

GUI からエージェントのサーバーで実行する処理は、メモリ上のキュー AgentJobs に入れ、エージェントが long poll（GET /api/agent/jobs、最大 25 秒待ち）で受け取って POST /api/agent/jobs/{id} で結果を返します。GUI のリクエストは結果が来るまで待ちます。サービス停止時は long poll を即座に打ち切ります。

エージェントの処理のうち Windows と Linux で共通の部分（AgentConfig、AgentOutbox、AgentSender、AgentSettingsSync、AgentJobRunner、AgentCommands）は Services/AgentCore.cs にあり、違う部分は IAgentPlatform（監査が有効か、ジョブの実行）で差し替えます。Windows は WindowsAgentPlatform（SACL）、Linux は LinuxAgentPlatform（Samba）です。

Linux エージェント

Samba で共有している Linux のファイルサーバー用。linux-agent/FileAccessMonitor.Agent.Linux.csproj（net10.0、linux-x64 の自己完結・単一ファイル）で、共通のソース（AgentCore.cs、AgentProtocol.cs、RecordingRules.cs、SettingsStore.cs、AppPaths.cs、AccessRecord.cs）をリンクして使います（LINUX_AGENT 定数で鍵ファイルの保存方法だけ切り替え）。systemd のサービス fileaccessmonitor-agent（Type=notify、root）として動き、データは /var/lib/fileaccessmonitor。

収集

  • Samba の full_audit モジュールが syslog に出す行を、journalctl --follow --output=json SYSLOG_IDENTIFIER=smbd_audit で読む。続きの位置はジャーナルのカーソルで、送信待ちフォルダと一緒に保存（agent-position.txt）
  • 行の形式（full_audit:prefix = %u|%I|%m|%S|%P）: ユーザー|接続元IP|端末名|共有名|共有のパス|操作|ok|引数…
  • create_file: 要求したアクセスマスクで読取・書込を判定（Windows と同じビット）。dir ならフォルダとして覚える。renameat は名前変更（元のパスで記録）、unlinkat は削除。Samba 4.14 より前は rename / unlink / rmdir
  • 監視フォルダ・記録ルール・読取のまとめ・フォルダの扱い（削除・名前変更のみ記録）は Windows と同じ。パスは大文字と小文字を区別
  • journald が流量制限で行を捨てると「Suppressed N messages」を記録するので、それを読んで記録の途切れ（gap.journalSuppressed）として通知。カーソルの位置がジャーナルから消えていた場合も通知（gap.journalRotated）。インストーラーは smbd に LogRateLimitIntervalSec=0 の drop-in を追加

監査の設定（applySacl / removeSacl）

  • フォルダを含む共有と、フォルダの中にある共有を smb.conf（smbd -b の CONFIGFILE）から探し、その共有のセクションに # FileAccessMonitor begin 〜 end の行（vfs objects に full_audit を加えたもの、full_audit:*）を追加（SambaConfigText）。共有の vfs objects は global のものを置き換えるため、今有効なモジュールを引き継ぐ
  • 置き換えた行は # FileAccessMonitor replaced: を付けてコメントにし、解除で元に戻す。解除は、他の監視フォルダが使っている共有では行わない
  • 書き換えは testparm -s で確認してから、バックアップ（smb.conf.fam-backup-日時）を残して置き換え、smbcontrol smbd reload-config。結果に kind: "samba" を付け、監視サーバーは「N 個の共有で監査を有効にしました」と表示
  • heartbeat の「監査」は、すべての監視フォルダが監査中の共有に含まれるか

監視サーバー側

PathText で Windows のパス（\、大文字小文字を区別しない）と Linux のパス（/ で始まる、区別する）を扱います。閲覧範囲は Linux のパスを substr の完全一致で絞り、未使用ファイル・フォルダ別の名前も区切り文字に合わせます。

Samba の収集部分（SambaAudit.cs、SambaConfig.cs、SambaPlatform.cs）は本体の Services/ にあり、Linux エージェントはそれをリンクします。収集部分は IRecordSink に渡すので、Linux 版の監視サーバーが自分自身を収集するときは DB（LocalRecordSink）に、エージェントでは送信待ち（RemoteRecordSink）に入ります。続きの位置は文字列（Windows はレコード ID、Linux はジャーナルのカーソル）です。

Linux の監視サーバー

拒否・権限変更・作成・USN（v1.9）

監査ポリシーと SACL（Windows）

SaclManagerService.EnableAuditPolicy() が次のサブカテゴリを auditpol で有効にします（setup-audit.ps1 も同じ。restore-audit.ps1 はハンドル操作の失敗を無効に戻す）。

サブカテゴリGUID設定理由
ファイル システム{0CCE921D-…}成功 + 失敗SACL のエントリが記録を出す条件
ハンドル操作{0CCE9223-…}失敗のみWindows 11 で確認: これがないと拒否された操作の 4656（失敗）が記録されない。成功は雑音になるので有効にしない
承認ポリシーの変更{0CCE9231-…}成功4670（権限の変更）のため

監査エントリ（SACL）は 1 つの規則に Success | Failure を付け、権利は ReadData・WriteData・AppendData・Delete に ChangePermissions | TakeOwnership を加えたもの（ReplaceAuditRule が Everyone のエントリを置き換えるので、再適用で旧 SACL が更新される）。フォルダをたどる際、サービスが開けないフォルダは飛ばして続けます。

拒否の記録

  • 4656 の Audit Failure。使う欄: SubjectUserName/DomainName/LogonId、ObjectType（File）、ObjectName、AccessMask、ProcessName。Status 欄があり 0xC0000022 以外なら無視
  • 種別（ParseDeniedType）: DELETE ビット → Delete、WriteData / AppendData / 汎用書込 → Write、ReadData / 汎用読取 → Read、それ以外（属性だけの要求など）は記録しない
  • DeniedMerger: 同じ (ユーザー, パス, 種別) は 60 秒（スライディング）で 1 件。辞書は上限付き
  • Linux（SambaAudit.cs）: full_audit:failure に create_file unlinkat renameat（4.14 より前は create_file unlink rename rmdir）を追加（RecordDenied が false なら none）。行の状態欄は ok または fail (strerror)。失敗行は、SambaErrno の表の「Permission denied」「Operation not permitted」（日本語 glibc の文言も）なら拒否。「No such file or directory」は、そのパスが実在するときだけ拒否（Samba は独自の NT アクセス判定で拒否し、古い errno が残るため。AuditAccess.OnlyIfExists、収集側が Exists を確認）。実在しないパスの失敗（クライアントの探索）や busy などは捨てる。同じ (ユーザー, パス, 種別) は 60 秒で 1 件（Services/DeniedMerger.cs）。失敗の監査は存在しないパスの試行も journald に出すため、ジャーナルの量が増える

権限変更

  • Windows: 4670 の OldSd / NewSd（SDDL）を PermissionChange.Describe（純粋関数）で比べ、所有者の変更、明示的な ACE の追加・削除（権利は FullControl / Modify / ReadAndExecute / Read / Write、他は 0x…）、継承の有効・無効を短い文にする（2000 文字で省略）。継承による変更だけなら inherited permissions changed。差がなければ記録しない。4663 の WRITE_DAC / WRITE_OWNER は種別なし（無視）
  • 雑音対策（PermissionMerger）: 同じ (ユーザー, パス) は 2 秒で 1 件。同じログオンの祖先のパスに 10 秒以内に記録済みなら、明示的な ACE の差がない子は捨てる
  • Linux: Samba の fset_nt_acl を成功操作に加える（SambaOps.Available が full_audit のモジュール内の操作名を調べ、無ければ権限変更は記録しない。未知の操作名はすべてを記録させてしまうため）。引数のパス末尾の ACL 文（path []）は除く。Detail は null（fchmod / fchown は解釈できるが既定では監査しない）。同じ (ユーザー, パス) は 3 秒で 1 件。変更前後は分からない
  • コピー: Windows はコピー時に新しいファイルのセキュリティ情報を設定するため、Permission が 1 件記録されることがある（既知の制限）

USN ジャーナル（Create と NewPath、Windows）

  • UsnJournalReader: 監視フォルダのあるボリュームのうち NTFS / ReFS（DriveInfo.DriveFormat）が対象。FSCTL_QUERY_USN_JOURNAL でジャーナル ID と位置を得て、500 ミリ秒ごとに FSCTL_READ_USN_JOURNAL（理由: FILE_CREATE、RENAME_OLD_NAME、RENAME_NEW_NAME。V2 / V3 の記録）。親の参照番号から OpenFileById + GetFinalPathNameByHandle でパスを求め（LRU キャッシュ）、監視フォルダの配下だけ解決する。ジャーナルは作らない（所有者の決定）: 無い（エラー 1179）・FAT / exFAT / ネットワーク・開けないボリュームは「使えない」とし、情報ログを 1 回出して従来の動作（Write、変更前のパスのみの Rename）。10 分ごとに再確認。ログの案内は fsutil usn createjournal m=33554432 a=…
  • 位置は usn-position.json（ボリューム → ジャーナル ID と次の USN）に Security の位置と一緒に保存し、再起動で古い Security イベントを読み直すときに合う範囲を読み直す。Recording.UsnCorrelation（settings.json、既定 true）で全体を切れる
  • UsnCorrelator（純粋、時刻は注入）: 作成と名前変更の事実を大文字小文字を区別せず保持（10 分、上限 10 万）。DeleteTracker の後の Write と Rename は保留し、ジャーナルが追いついた（CaughtUpUtc ≥ アクセス時刻 + 3 秒）、実時間で 10 秒、停止時のいずれかで解放。Write は creates[パス] が (−30 秒, +2 秒) にあれば Create に（1 回だけ消費）。Rename は renames[旧パス] が (−1 秒, +10 秒) にあれば NewPath を付ける。拒否と権限変更の記録は保留しない。使えないボリュームは素通し
  • 制限: ジャーナルにユーザーがないので、Security ログに記録のない作成・名前変更は記録しない。ジャンクション・シンボリックリンク・8.3 名は解決しない。長い停止のあとはジャーナルが範囲を持っている場合だけ補える。監視フォルダ外からの移動は記録されない
  • Linux: create_file の引数 アクセスマスク|file/dir|disposition|パス のうち、disposition が create かつ file なら Create。open_if / overwrite_if / supersede は区別できないので Write（Create は下限値）。renameat / rename の 旧|新 から NewPath

エージェント通信のバージョン（protocol 2）

AgentRecord に Denied、NewPath、Detail を追加。AgentProtocol.Version = 2 で、heartbeat の応答の protocol に入れる。AgentSender は応答の protocol が 2 未満（または未確認。最初のバッチの前に heartbeat を送る）なら、送信時に AgentProtocol.ForServer で、拒否・Permission の記録を落とし、Create を Write にし、NewPath / Detail を外す。送信待ちのファイルは書き換えないので、サーバーを更新すれば完全な内容が届く。1.8 のエージェントが送るとき、欠けた項目は既定値（false / null）になり、古いサーバーは未知のプロパティを無視する。

v1.10 の追加（ファイルの履歴・アクセス権・定期レポート・改ざん検知）

1.10 は 4 つの機能を追加します。下の記述は実装（コードが正）に合わせてあります。各機能の詳細な契約は、そのクラスのコメントを参照してください。

ファイルの履歴（FileHistory、history.js）

  • 入口: 最新アクセス・検索結果のファイル名（recordNameHtml → historyButtonHtml）、ファイル・フォルダの詳細ダイアログのタイトル、アクセス権タブの行。ダイアログは #historyModal。
  • アルゴリズム（Services/FileHistory.cs、IHistorySource を介した純粋な処理。DB なしで試験できる）: 起点（サーバー、パス、at の時刻）から、後ろ向きには「移動先が今のパスの名前変更」（ファイル）と「祖先フォルダの名前変更」を、前向きには「移動元が今のパスの名前変更」「祖先フォルダの名前変更・削除」「ファイルの削除」をたどる。区間ごとに記録を取り、同じ秒の並びは Id で決める。
  • 上限: 区間は最大 50（MaxHops）、祖先は 32 階層まで、既定 500 ステップ（要求で最大 2,000）。上限に当たったら truncated を立て、end は hopLimit または windowLimit。
  • 範囲: たどる処理は範囲に関係なく全件で行い、出力は範囲内だけ。範囲外の区間は gap(outOfScope) にまとめ、パスは出さない。移動先が範囲外なら move として表示し、newPath は null。
  • 索引: 既存の (FilePath, AccessTime) と、NewPath の部分インデックス（COLLATE NOCASE）。索引で候補を取り、比較は OS の規則で行う（Windows のパスは大文字小文字を区別しない）。
  • 制限: フォルダの名前変更・移動は、そのフォルダで「削除」を監視しているときだけ記録される（名前変更は削除の種類と一緒に記録されるため）。画面の説明文にもその旨を書いてある。

アクセス権レポート（PermissionScanWindows、PermissionScanLinux、PermissionAnalysis、PermissionReportService、PermissionsController、permissions.js）

  • 収集（Windows）: 各フォルダで DirectoryInfo.GetAccessControl（Access と Owner）。AreAccessRulesProtected で継承の中断を判定する。再解析点（ジャンクション、シンボリックリンク）はたどらない。SID は名前に 1 回だけ変換し、全体で 5 秒の予算を超えたら SID のまま。読めないフォルダは「読めない」の行。権限は Read=1, Write=2, Delete=4, Perm=8, Exec=16 のビット。
  • 収集（Linux）: モードビットと所有者・グループ（libc を P/Invoke し、名前は getpwuid_r / getgrgid_r で解決）。POSIX ACL は getxattr("system.posix_acl_access") と system.posix_acl_default をバイナリとして解析する（getfacl は使わない。ツールがないマシンがあるため）。共有は testparm -s から、guest ok、read only、valid users、write list、vfs objects に acl_xattr / acl_tdb があるか（NT ACL 警告の判定）を読む。
  • 分類（PermissionAnalysis、サーバー側。エージェントを更新せずに規則を変えられる）: 広い主体は SID で判定する（Everyone S-1-1-0、Authenticated Users S-1-5-11、BUILTIN\Users S-1-5-32-545、Guests S-1-5-32-546、Anonymous S-1-5-7、Network S-1-5-2、Interactive S-1-5-4、ドメインの Users・Guests・Computers は -513・-514・-515）。名前は表示用で、判定には使わない（表示言語で変わるため）。Linux は other と広いグループ名、settings.json の Permissions:BroadPrincipals（追加の名前、大文字小文字を区別しない）。
  • 重要度: 変更・削除・権限変更を許す（Write、Delete、Perm のいずれか）= high、読取りだけ = medium。拒否のエントリは警告にせず一覧に出すだけ。共有は guestOk かつ書込可 = high、guestOk かつ読取専用 = medium。
  • 結果（Services/PermissionContract.cs、ジョブ permissions）: 引数は { path, maxFolders, maxFiles, maxDepth, includeFiles, timeLimitSeconds }。既定と上限は、フォルダ 5,000 / 20,000、ファイル 50,000 / 200,000、深さ 8 / 32、時間 300 / 900 秒（エージェントが上限に丸める）。行は最大 20,000（MaxRows）、エラーは最大 100。行のフラグ: 1 フォルダ、2 継承の中断、4 読めない、8 明示のエントリあり、16 POSIX ACL、32 既定の ACL、64 所有者が親と違う。打ち切りは limit（folders、files、time、depth、rows）で示す。
  • 保存: <データフォルダ>/permission-reports/<サーバー>__<root の SHA-1>.json。最新 1 回だけ。一時ファイルを経て置き換える。ジョブのタイムアウトは timeLimitSeconds + 60 秒（超えると 504 agents.noAnswer）。
  • 権限変更の印: 結果の各行について、同じサーバーの AccessType = Permission（拒否ではない）の最新の記録（時刻、ユーザー、記録 Id）を引く。スキャン時刻より新しければ changedSinceScan（「スキャン後に変更」）。
  • 権限の範囲: 閲覧は Admin と範囲を持つ Viewer。スキャンは Admin のみ（実行に時間がかかり、エージェントの他のジョブを待たせるため）。
  • 互換: 1.10 未満のエージェントには送らず 409 perm.agentTooOld。ジョブの応答が Unknown job で始まる場合も同じ扱い。

定期レポート（ReportSettings、ReportSchedule、ScheduledReportService、ReportBuilder、ReportHtml、ReportsController）

  • 設定: settings.json の Reports（既定 Enabled = false、Frequency = weekly、DayOfWeek = 1（月曜）、DayOfMonth = 1（1〜28）、Time = 09:00（サーバーのローカル時刻）、Csv = true、ScopedViewers = true、Webhook = false、TopN = 10（1〜50））。SMTP と言語は通知設定（AlertSettings）から取り、SMTP がなければ有効にできない。
  • スケジュール（ReportSchedule、純粋関数）: 期間は直前の 1 日・1 週・1 か月。キャッチアップは日次 6 時間、週次 24 時間、月次 48 時間で、それを過ぎた枠は送らず report.skipped（reason=missed）。存在しない時刻（夏時間の切替え）は隙間の分だけ進め、重複する時刻は初回を使う。
  • 状態（CollectorStates）: Report.LastSlot（処理した最後の枠）、Report.Attempts（枠・回数・UTC）、Report.LastSent。有効にした時、または頻度・曜日・時刻を変えた時は、LastSlot を直前の枠に合わせ、すぐには送らない。テスト送信は LastSlot に触れない。
  • 再試行と同時実行: 送信の失敗は 15 分ごとに 3 回まで（MaxAttempts = 4）、その後は report.skipped（reason=failed）。送信は SemaphoreSlim(1) で 1 件ずつ。テスト送信は実行中なら 409 report.busy。
  • 宛先: 主な宛先は AlertSettings.MailTo で、全サーバーの範囲なしの内容。範囲つきの宛先は UserScopes のうち NotifyEmail があり、SendReport が true、Paths がある Viewer（1 回最大 50 通。超えた分は本文と操作ログに残す）。範囲つきには、アラート・エージェント・改ざん検知を入れず、権限は範囲内の行だけ。
  • 内容（ReportBuilder）: 種別ごとの件数と前の期間との差、拒否（別に数える）、権限変更（最新 20 件）、上位のファイル・フォルダ・ユーザー、保存済みスキャンの広いアクセス（高・中の件数、高の上位 20 件、14 日より古いスキャンは「古い」、未スキャンのルートは「未スキャン」。レポートはスキャンを開始しない）。管理者だけ: 送信したアラート（alert.sent を種別ごと）、エージェントの状態、改ざん検知の状態と FAM-ANCHOR の行。
  • 添付: broad-permissions.csv、permission-changes.csv、denied.csv、top-files.csv、top-users.csv。1 ファイル最大 20,000 行、合計 8 MB。超えたら大きいものから外し、本文にその旨を書く。CSV は UTF-8（BOM 付き）で、数式の先頭文字を無効化する。
  • HTML: インラインの CSS とテーブルだけ（画像・外部リソースなし、最大幅 720 px）。値はすべて HTML エンコードする（ファイル名は利用者が決められるため）。テキスト版は同じモデルから作る。
  • Webhook: 主な宛先の数値の要約だけ（期間、件数、拒否、権限変更、高の広いアクセス、改ざん検知の状態。ファイル名は入れない）。範囲つきには送らない。
  • 操作ログ: report.settings、report.test、report.sent（recipients, scoped, failed, slot）、report.skipped。

改ざん検知（ChainInterceptor、ChainHash、IntegrityService、IntegrityBackgroundService、RetentionService、AnchorLog、SecretStore）

  • 鍵: chain.key（データフォルダ、32 バイトの乱数、SecretStore.GetOrCreateChainKey()）。Windows は SYSTEM / Administrators のみ読み取り可、Linux は所有者だけ読み書き可。KeyId は鍵の SHA-256 の先頭 8 桁（checkpoint に保存）。
  • チェーン: 2 本（access = AccessRecords、audit = AuditLogs）。ChainHash = HMAC-SHA256(鍵, 前のハッシュ || 正準形式)。正準形式は、チェーン名、ChainSeq、サーバー名、UTC の ticks、種別、Denied、IsFolder、ユーザー、パス、ファイル名、フォルダ、IP、端末名、NewPath、Detail（audit は Time、ユーザー、Action、Detail、IP）を、フィールドごとに長さ（4 バイト）と UTF-8 の値で連ねたもの（null は長さ -1）。Id は含まない（DB が後で振るため）。
  • 書込み（ChainInterceptor、SaveChangesInterceptor）: 追加された行があると、プロセス内のロック（SemaphoreSlim）を取り、連番を振ってヘッドの更新を同じ SaveChanges（同じトランザクション）に入れる。ロックは完了・失敗・キャンセルで解放し、30 秒のウォッチドッグで必ず解放する。失敗時はヘッドを DB から読み直す。チェーンの順は挿入の順で、AccessTime の順ではない（エージェントの遅れた送信のため。だから保持期間の削除も先頭からの接頭辞になる）。
  • 検証（IntegrityService）: 増分は 15 分ごとに、前回の検証位置から。全件は毎日 03:30（ローカル時刻）と、手動（POST verify）。どちらも短いページ単位で読む（SQLite のロールバックジャーナルは長い読取りで書込みを止めるため）。検出の種類: altered、missing、truncatedTail、headMismatch、headRollback、unchained、checkpoint、keyChanged、duplicate。1 か所の改変は 1 件として報告し、以後の行は保存されたハッシュを前として続ける。
  • chain-head.json（データフォルダ、SYSTEM / Administrators のみ）: 確認済みの各チェーンの末尾（Seq、Hash、keyId）。古い DB に戻されたこと（headRollback）を見つけるために使う。中身が改ざんされていれば無視して警告を出す。
  • 保持期間（RetentionService.CleanupAsync）: 鍵があるとき、チェーンの先頭から、保持期間内で最初に残す記録の直前までを削除し、ChainCheckpoint（reason retention、Mac = HMAC(鍵, chain, UpToSeq, Hash, KeyId, 前の Mac)）を書く。ChainSeq が null で Id ≤ LegacyMaxId の旧行は、従来どおり時刻で削除。遅れて届いた古い日付の記録は、前の記録が消えるまで残る。
  • 初回起動（SchemaV110Integrity）: 既存の行は計算しない。LegacyMaxId と LegacyCount を記録し、genesis の checkpoint とヘッド（Seq 0）を作る。新しい DB は件数 0。
  • 承認（POST accept）: 現在の検証済みの位置に、reason accepted の checkpoint を書く。検出は一覧に残る（承認済み）。
  • アンカー: 毎日 00:05（ローカル時刻）に 1 回。起動が遅れても、その日のうちに 1 回書く。行の形式は FAM-ANCHOR v1 server=… chain=access seq=… hash=… time=… audit-seq=… audit-hash=…。書込み先は、Windows はアプリケーションログのソース FileAccessMonitor のイベント 1100（ソースがなければ作成を試み、作れなければ Application ソースを使う）、Linux は syslog（facility local5、タグ fileaccessmonitor）、そして操作ログ integrity.anchor。Integrity.AnchorNotify（settings.json の "Integrity": { "AnchorNotify": true }、既定 false）がオンなら通知にも送る。定期レポートの本文にも入る。
  • 取り出しと照合: GET anchor は署名付き JSON（format: fam-anchor-v1、mac は鍵による署名）。POST check-anchor は行または JSON を受け、同じ seq の ChainHash と比べる。その位置が保持期間で消えていれば checkpoint と比べる。
  • 通知: 新しい検出（チェーン・種別・最初の seq で識別）は NotifyAsync（種別 Integrity、高優先度。通知が有効なときだけ）と、操作ログ integrity.break。未承認の間は 24 時間ごとに再通知（Integrity.AlertedSignature、Integrity.AlertedAt）。
  • 画面: 設定の「改ざん検知」カード（#integritySettingsSection、Admin）と、未承認の検出がある間の上部の赤い帯（#integrityBanner、全ての管理者画面）。

通知

Webhook（Teams Workflows / Slack / 汎用 JSON）とメール（SMTP）。通知が有効なときだけ送ります。送信結果は操作ログ alert.sent に残します。Webhook はプロキシ（URL・ユーザー・パスワード）を指定できます。サービスは SYSTEM で動くため Windows のユーザーのプロキシ設定は使えず、アプリ側で指定します（メールは使わない）。

種類条件
大量の削除・書込・読取1 人のユーザーが集計時間（既定 5 分）内にしきい値以上（削除の既定 100、書込・読取は 0 = オフ）。読取はまとめた後の件数。フォルダは数えない。再通知までの間隔あり。通知にはサーバー名を含める
記録の途切れSecurity ログの消去、または収集前の上書き
エージェントの無応答・復旧既定 15 分以上接続がない（AgentOfflineMinutes、0 = オフ）／再び接続した
改ざん検知新しい検出（チェーン・種別・最初の位置）。緊急（高優先度）として送り、未承認の間は 24 時間ごとに再通知（v1.10）。alert.sent の種別は Integrity
フォルダごとの通知先閲覧範囲と通知先メールを持つ Viewer には、範囲内の記録だけで別途検知した大量操作をメールで送る（しきい値は共通）

多言語対応（i18n）

画面は wwwroot/lang/ja.js と en.js（window.I18N_JA / I18N_EN）。HTML は data-i18n / data-i18n-ph / data-i18n-title、JS は t(key, vars)（{n} などを置換）。API のメッセージは Services/Messages.cs で、Accept-Language に従います。通知は通知設定の言語で送ります。

注意：言語ファイルは単一引用符の JS 文字列です。値にアポストロフィ（'）や単独のバックスラッシュを入れると、ファイル全体が読み込めなくなります（バックスラッシュは \\）。キーの重複も後勝ちで上書きされます。

認証・ロール・閲覧範囲

JWT Bearer（既定 24 時間）。トークンにはセキュリティスタンプを入れ、ユーザーの削除・ロール変更・パスワード変更で即時に無効になります。

ロール権限
Viewer閲覧（ダッシュボード・一覧・検索・CSV）、自分のパスワード変更。閲覧範囲があればその範囲だけ、加えて範囲内の未使用ファイル
Admin全体の閲覧と、すべての設定・ユーザー・エージェント・通知・操作ログ

閲覧範囲

Viewer ごとに「サーバー＋フォルダ」（サーバー省略で全サーバー）を割り当てます。範囲がない Viewer と Admin は全体を見られます。範囲はリクエストのたびに DB から読み、統計・CSV・保持の件数・未使用ファイルに適用します。

デプロイ
