# FileAccessMonitor

[English](README.md) | 日本語

ファイルサーバーの共有フォルダへのアクセス（読み取り・書き込み・作成・削除・名前変更・権限変更、および拒否された試み）を記録・集計し、Web GUI で可視化するツールです。Windows のファイルサーバーはセキュリティ監査ログから、Samba で共有している Linux のファイルサーバーは Samba の監査ログから収集します。複数のファイルサーバーの記録を、エージェントで 1 台の監視サーバーに集められます。監視サーバーは Windows でも Linux でも動きます。

![ダッシュボード](docs/images/dashboard-ja.png)

> [!IMPORTANT]
> 本ツールは「誰が・いつ・どのファイルにアクセスしたか」を記録します。組織で利用する場合は、就業規則やプライバシーポリシー等に基づき、監視対象となる利用者へ事前に周知してください。

## 構成と必要環境

FileAccessMonitor は次の 2 つの役割で動きます。

- **監視サーバー**: Web 画面・データベース・通知を持ち、記録を集めて表示します。自分自身の共有フォルダのアクセスも記録する（**1 台構成**）か、エージェントから届いた記録だけを表示する（**監視サーバーのみ**）かを選べます
- **エージェント**: 監視したいファイルサーバーに入れ、そのサーバーのアクセスを記録して監視サーバーに送ります。Web 画面はありません

ファイルサーバーが 1 台なら、そのサーバーに監視サーバー（1 台構成）を入れるだけで使えます。2 台目以降のファイルサーバーにはエージェントを入れます。

| | 監視サーバー（Windows） | 監視サーバー（Linux） | エージェント（Windows） | エージェント（Linux） |
|---|---|---|---|---|
| OS | Windows Server 2016 以降、Windows 10/11 | systemd が動く x86-64 の Linux（Rocky Linux 9.4 で確認） | Windows Server 2016 以降、Windows 10/11 | systemd が動く x86-64 の Linux（Ubuntu 24.04、Rocky Linux 9.4 で確認） |
| 記録する対象 | 1 台構成の場合: このサーバーの共有フォルダ（Windows の監査ログ） | `--collect` の場合: このサーバーの Samba 共有 | このサーバーの共有フォルダ（Windows の監査ログ） | Samba 4.x の共有（SMB 経由のアクセス） |
| 権限 | 導入に管理者権限（Web GUI のサービスは権限なしで動作。ローカル収集では 2 つ目のサービス「コレクター」が SYSTEM で動作） | 導入に root（Web GUI は専用ユーザーで動作。`--collect` では 2 つ目のサービス「コレクター」が root で動作） | 導入に管理者権限（SYSTEM で動作） | root |
| ネットワーク | 受信: TCP 8080（Web 画面）、8443（エージェント） | 受信: TCP 8080、8443 | 送信: 監視サーバーの 8443 のみ | 送信: 監視サーバーの 8443 のみ |
| 配布ファイル | `FileAccessMonitor-Setup-<版>.exe` | `fileaccessmonitor-server` の rpm / deb（または tar.gz） | `FileAccessMonitor-Setup-<版>.exe`（役割で「エージェント」を選択） | `fileaccessmonitor-agent` の rpm / deb（または tar.gz） |
| 手順 | [インストーラーで導入する](#インストーラーで導入する推奨) | [8. Linux の監視サーバー](#8-linux-の監視サーバー) | [6. 複数のファイルサーバーから収集する](#6-複数のファイルサーバーから収集するエージェント) | [7. Linux のファイルサーバー](#7-linux-のファイルサーバーsamba-エージェント) |

- どれも自己完結型で配布するため、.NET ランタイムのインストールは不要です（ソースからビルドする場合のみ .NET 10 SDK が必要）
- Web 画面は、監視サーバーにつながる PC のブラウザ（Edge、Chrome、Firefox など）で使います
- エージェントから監視サーバーへの接続だけを使い、監視サーバーからファイルサーバーへは接続しません

## セットアップ

### インストーラーで導入する（推奨）

[Releases](https://github.com/nuts-i77/FileAccessMonitor/releases) から `FileAccessMonitor-Setup-<バージョン>.exe` をダウンロードし、Windows のファイルサーバー（監視サーバーを別のマシンにする場合はそのマシン）で実行します。インストーラーは次の処理を行います。

- `C:\Program Files\FileAccessMonitor` にインストール
- Windows サービスを登録して起動: `FileAccessMonitor`（Web GUI とデータベース。仮想サービスアカウント `NT SERVICE\FileAccessMonitor` で、権限なしで動作）と、監視サーバーのみを選んだ場合を除き `FileAccessMonitorCollector`（「File Access Monitor Collector」。SYSTEM で動作し、アクセスの記録と監査の設定を担当）。エージェントの導入では、サービスは `FileAccessMonitor`（SYSTEM）のみです。詳しくは[どのアカウントが何を実行するか](#どのアカウントが何を実行するか)を参照してください
- サーバーの使い方を選択: **1 台構成 / 監視サーバー**（このサーバーのアクセスを記録し、Web GUI を表示）、**監視サーバーのみ**（Web GUI を表示し[エージェント](#6-複数のファイルサーバーから収集するエージェント)から記録を受け取る。このサーバー自身のアクセスは記録せず、監査の設定も変更しない）、**エージェント**
- Web GUI のポートを指定（既定値は 8080）。必要なら FileAccessMonitor.exe の受信を許可するファイアウォール規則も追加（Web GUI のポートとエージェント用ポート 8443）

新しいバージョンのインストーラーを実行すると、設定を引き継いだまま上書き更新します。インストール後は [3. 初回ログイン](#3-初回ログイン) に進んでください。

初回ログインのあと、**導入ウィザード**が開きます。admin のパスワードの変更、ファイルサーバーの選択（エージェントがあるとき）、最初の監視フォルダの追加、Security ログのサイズの拡張（Windows。推奨は 1 GB）、最初の記録が届くことの確認を、順に行います。［あとで］で閉じても、**設定** タブの［導入ウィザード］からいつでも開けます。以下の 3〜5 は、ウィザードが行う内容の説明です。

> [!NOTE]
> インストーラーはコード署名していないため、Windows SmartScreen の警告が表示されることがあります。**詳細情報** → **実行** で続行してください。ダウンロードしたファイルが正しいか確かめる方法は「[ダウンロードしたファイルの検証](#ダウンロードしたファイルの検証)」を参照してください。

ソースからビルドする場合は、以下の 1・2 の手順を行います。

### 1. ビルド（開発 PC）

```powershell
.\build.ps1
```

`publish\` フォルダに自己完結型の EXE が出力されます。

### 2. サービスのインストール（サーバー上、管理者 PowerShell）

`publish\` と `install-service.ps1` をサーバーへコピーして実行します。

```powershell
.\install-service.ps1
```

- Windows サービス `FileAccessMonitor` と `FileAccessMonitorCollector` として登録・自動起動（[どのアカウントが何を実行するか](#どのアカウントが何を実行するか)を参照）
- FileAccessMonitor.exe のファイアウォール受信規則を追加（TCP 8080、エージェント用の 8443）

WinRM が使える環境では、開発 PC からビルドとデプロイを一度に行えます。

```powershell
.\deploy-remote.ps1 -ServerIP <サーバー名または IP>
```

### 3. 初回ログイン

ブラウザで `https://<サーバー>:8080` を開きます（新規インストールは自己署名証明書の HTTPS なので、ブラウザーに警告が一度表示されます。1.9 より前から更新した環境は、切り替えるまで `http://` のままです。[通信の暗号化](#セキュリティ)を参照）。

- ユーザー名: `admin`
- パスワード: 初回起動時にランダム生成され、サーバーの以下のファイルに保存されます（SYSTEM / Administrators と Web GUI のサービスアカウントのみ読み取り可）

  ```
  C:\ProgramData\FileAccessMonitor\initial-admin-password.txt
  ```

ログイン後、画面右上のユーザーメニュー → **パスワード変更** で変更してください。変更するとこのファイルは自動的に削除されます。

### 4. 監視フォルダの追加

**設定** タブで監視するフォルダ（例: `D:\Share`）を追加します。追加時に、監査ポリシー「ファイル システム」（成功と失敗）、「ハンドル操作」（失敗のみ。これがないと拒否された操作はログに残りません）、「承認ポリシーの変更」（成功。権限変更用）の有効化と、指定フォルダ配下への SACL（監査エントリ。成功と拒否の読み取り・書き込み・削除、権限と所有者の変更が対象）の設定が自動で行われます。接続元 IP の取得に使う監査ポリシー「ファイルの共有」は、サービス起動時に自動で有効化されます。

1.9 より前から更新した場合は、すでにある監視フォルダごとに **SACL 再適用** を 1 回押してください（Linux の共有でも同じボタンで Samba の監査を設定し直します）。押すまでは、拒否されたアクセスと権限変更は記録されません。まだ必要なフォルダは設定画面に表示されます。

監査設定をスクリプトで行う場合は `setup-audit.ps1 -SharePaths "D:\Share"` を、元に戻す場合は `restore-audit.ps1 -SharePaths "D:\Share"`（ハンドル操作の監査も無効に戻します）を使います。

#### Windows での作成と名前変更（USN ジャーナル）

Security ログには、ファイルの作成も、名前変更後の名前も含まれません。FileAccessMonitor は、監視フォルダのあるボリュームの NTFS 変更ジャーナル（USN ジャーナル）からこれらを読み取ります。これにより、アクセスで作られたファイルは書き込みではなく **作成（Create）** として記録し、名前変更・移動では新しいパスも表示します。FileAccessMonitor はジャーナルを**作りません**。ジャーナルのないボリューム（および FAT、exFAT、ネットワークのパス）は、これまでと同じ動作（書き込み、名前変更は変更前のパスのみ）で、その旨をボリュームごとに 1 回サービスのログに出します。ジャーナルとの突き合わせのため、記録の保存はこれまでより数秒遅れます。

ボリュームの確認と、これらの記録が必要な場合のジャーナルの有効化は次のとおりです（管理者 PowerShell。システムの変更で、最大 32MB を使います）。

```powershell
fsutil usn queryjournal D:
fsutil usn createjournal m=33554432 a=8388608 D:
```


### 5. Security ログのサイズを拡張する（推奨）

Windows の Security ログは既定で 20MB 程度しかなく、アクセスの多い環境では数時間で古いイベントが上書きされます。本ツールはリアルタイムで収集するため記録自体は残りますが、サービスの停止中に上書きされた分は記録できず、調査時に元イベントも確認できないため、拡張を推奨します。導入ウィザードの Security ログの手順か、**設定** の「サーバーごとの設定」にある **Security ログ** で、サーバーごとに設定できます（エージェントのサーバーも、監視サーバーの画面から設定できます。1.12 以降の Windows エージェントが必要）。コマンドで行う場合は次のとおりです。

```powershell
wevtutil sl Security /ms:1073741824   # 1GB
```

### 6. 複数のファイルサーバーから収集する（エージェント）

1 つの画面で、複数のファイルサーバーの記録を見られます。Web GUI を表示するサーバー（監視サーバー）には通常どおりインストールし、他のファイルサーバーには **エージェント** としてインストールします（収集と送信のみを行います）。監視サーバーはファイルサーバーの 1 台でも、**監視サーバーのみ** としてインストールした別のマシン（Windows または [Linux](#8-linux-の監視サーバー)）でも構いません。

インストール済みの監視サーバーで、自分自身のアクセスを記録するか（監視専用にするか）を切り替えるには、管理者の PowerShell で `C:\Program Files\FileAccessMonitor` にある `FileAccessMonitor.exe local-collection off`（または `on`）を実行し、サービスを再起動します。このコマンドは設定を変えるだけなので、コレクターのサービスも有効化または無効化してください。`sc.exe config FileAccessMonitorCollector start= auto` と `sc.exe start FileAccessMonitorCollector`（無効にする場合は `start= disabled` と `sc.exe stop FileAccessMonitorCollector`）を実行します。インストーラーをもう一度実行しても同じ設定になります。Linux では `sudo fileaccessmonitor-server --collect` または `--monitor-only` がすべて行います。今の状態は **設定 → アプリ情報** に表示されます。

1. ファイルサーバーから監視サーバーの TCP **8443**（エージェント用ポート）に接続できるようにします。監視サーバーは常にこのポートで待ち受けており、インストーラーのファイアウォールのオプションで許可できます。この規則は FileAccessMonitor.exe を許可するので、Web GUI のポートとエージェント用ポートの両方が対象です
2. **設定 → エージェント** で **登録コードを発行** を押します。ファイルサーバーから監視サーバーへ別の名前や IP アドレスで接続する場合は、アドレスを変更して **反映** を押します。表示された接続文字列をコピーします（24 時間有効、1 回だけ使えます）。このコードで登録できるのは、まだ登録されていないサーバーだけです。ファイルサーバーの再インストール後などにエージェントを登録し直す場合は、一覧のそのエージェントの行にある鍵のボタンから発行します。そのコードは、そのエージェントの再登録にしか使えません。監視サーバー自身と同じ名前では、どのコードでも登録できません
3. ファイルサーバーでインストーラーを実行し、**エージェント** を選んで接続文字列を貼り付けます。インストール済みのサーバーをエージェントにする場合は、管理者の PowerShell で次を実行します

   ```powershell
   & "C:\Program Files\FileAccessMonitor\FileAccessMonitor.exe" enroll <接続文字列>
   Restart-Service FileAccessMonitor
   ```
4. ファイルサーバーの管理者 PowerShell で次を実行し、共有フォルダの監査を設定します。`-ExecutionPolicy Bypass` を付けると、スクリプトの実行が無効な環境でもこのスクリプトだけを実行できます

   ```powershell
   powershell -ExecutionPolicy Bypass -File "C:\Program Files\FileAccessMonitor\scripts\setup-audit.ps1" -SharePaths "D:\Share"
   ```

仕組みと制限:

- 1.8 のエージェントは 1.9 の監視サーバーとそのまま使えます。1.9 のエージェントから 1.8 のサーバーに送るときは、新しい情報なしで送ります（拒否と権限変更の記録は送らず、作成は書き込みとして送り、新しいパスは付けません）。送信待ちの記録は書き換えないため、サーバーを更新すれば完全な内容で届きます
- 接続は常にエージェントから監視サーバーに向かいます（監視サーバーからファイルサーバーへは接続しません）。通信は HTTPS で、証明書は監視サーバーが自動で作成します。エージェントはその証明書だけを信頼する（指紋を接続文字列に含めています）ため、認証局は不要です
- 記録は、監視サーバーが保存するまでエージェントの送信待ちフォルダ（`C:\ProgramData\FileAccessMonitor\outbox`、最大 2 GB）に残るため、監視サーバーに接続できない間も失われません
- 送信待ちフォルダが満杯（2 GB）になっても、エージェントは記録を破棄しません。そのサーバーでの収集を一時停止し、30 秒ごとに空きを確認します。記録は Security ログ（Linux ではジャーナル）に残り、監視サーバーに再び接続できて、送信待ちのデータを送り終えた後に収集されます。ただし、ログが上書きされる前であることが条件です。先に Security ログが上書きされた場合は、既存の記録中断の通知で欠けた範囲が報告されます（Linux のエージェントは、読み取りを再開した時点でジャーナルのローテーションを検知します）。この状態はエージェントのハートビートで報告され、［エージェント］タブに［送信待ちが満杯］と表示され、（通知が有効な場合は）通知が 1 回送信されます。負荷の高いサーバーでは、Security ログのサイズを大きくしてください。
- 複数のサーバーから記録が届くと、画面上部にサーバーの絞り込みが表示され、一覧に **サーバー** の列が加わります。削除したエージェントを絞り込みに出さない場合は、**設定 → エージェント** のスイッチをオンにします（記録は残り、［全サーバー］で表示されます）
- 監視フォルダと記録ルールはサーバーごとに設定します（**設定** タブ上部でサーバーを選択）。エージェントは 1 分以内に変更を取り込みます。エージェントのサーバーに監視フォルダを追加すると、エージェントがフォルダの存在確認と監査エントリ（SACL）の設定を行います。**未使用ファイル** タブでは、選んだサーバーのファイルをエージェント経由で調べます。これらはエージェントが接続中である必要があります。監視フォルダを設定するまでは、エージェントはそのサーバーで監査されたすべてのアクセスを記録します
- 閲覧範囲では、フォルダごとにサーバーを指定できます（「全サーバー」はどのサーバーの同じパスも対象）
- **エージェント** の一覧には、OS（Windows か Linux か）、最終接続、バージョン（監視サーバーと異なる場合は「要更新」と、そのファイルサーバーで実行する更新コマンドを表示する［更新手順］）、送信待ちの件数、ファイルアクセスの監査が有効かを表示します。通知が有効な場合、15 分（変更可、0 で通知しない）以上接続がないエージェントを通知し、復旧したときも通知します
- アラートや通知には、アクセスが発生したファイルサーバー名が入ります
- 記録の時刻は各ファイルサーバーの時計に基づきます。サーバー間の時刻を同期してください（NTP。ドメイン参加マシンは既定で同期されます）
- `FileAccessMonitor.exe unenroll` でエージェントを 1 台構成に戻せます

エージェント用ポートを変更する手順:

1. 監視サーバーの `C:\ProgramData\FileAccessMonitor\settings.json` に次を追加します。ファイル内の他の設定は残してください

   ```json
   "Agents": { "Port": 9443 }
   ```
2. `Restart-Service FileAccessMonitor` でサービスを再起動します。インストーラーが作るファイアウォール規則はポートではなくプログラムを許可するので、変更は不要です
3. 登録済みのエージェントは古いアドレスのままです。接続文字列を発行し直し、各ファイルサーバーで `FileAccessMonitor.exe enroll <接続文字列>` を実行してサービスを再起動してください

エージェントを使わず、ポートを開けたくない場合は、代わりに `"Agents": { "Enabled": false }` を指定します。

### 7. Linux のファイルサーバー（Samba エージェント）

Samba でフォルダを共有している Linux のファイルサーバーからも、監視サーバーに記録を送れます。Linux 版エージェントは、Samba の `full_audit` モジュールが出す監査ログを systemd のジャーナルから読みます。記録するのは SMB 共有経由のアクセスです（NFS や、サーバー上での直接の操作は対象外）。

必要なもの: systemd と Samba 4.x が動く x86-64 の Linux（Ubuntu 24.04 + Samba 4.19、Rocky Linux 9.4 + Samba 4.23 で確認。Debian、RHEL、AlmaLinux も同じ手順）と root 権限

1. リリースページから、ディストリビューションに合ったパッケージをダウンロードします。RHEL・Rocky・Alma は `fileaccessmonitor-agent-<バージョン>-1.x86_64.rpm`、Ubuntu・Debian は `fileaccessmonitor-agent_<バージョン>-1_amd64.deb` です
2. 監視サーバーの **設定 → エージェント** で接続文字列を発行し、root で次を実行します

   ```sh
   sudo dnf install ./fileaccessmonitor-agent-<バージョン>-1.x86_64.rpm     # または: sudo apt install ./fileaccessmonitor-agent_<バージョン>-1_amd64.deb
   sudo fileaccessmonitor-agent enroll <接続文字列>
   sudo systemctl enable --now fileaccessmonitor-agent
   ```
   パッケージ管理を使わない場合は `FileAccessMonitor-<バージョン>-linux-x64-agent.tar.gz` を展開し、`sudo sh install.sh <接続文字列>` を実行します。

   エージェントは systemd のサービス `fileaccessmonitor-agent` として動きます（ログ: `journalctl -u fileaccessmonitor-agent`）。データは `/var/lib/fileaccessmonitor` にあります。更新は、新しいパッケージを同じように `dnf install` / `apt install` します
3. 都合のよいときに Samba を 1 回再起動します（`systemctl restart smbd`。RHEL 系は `smb`）。監査ログが大量に出たときに journald が捨てないよう、インストーラーが設定を追加しており、Samba の再起動で有効になります
4. 監視サーバーの **設定** タブで Linux のサーバーを選び、`/srv/share/docs` のように Linux のパスで監視フォルダを追加します

Windows との違い:

- 監視フォルダを追加すると、そのフォルダを含む（またはその中にある）Samba の共有で、`smb.conf` を書き換えて監査を有効にします。書き換える前に `testparm` で新しい設定を確認し、バックアップ（`smb.conf.fam-backup-<日時>`）を残してから Samba に読み込み直させます。追加した行は `# FileAccessMonitor begin` と `# FileAccessMonitor end` の間にあり、置き換えた行（共有ごとの `vfs objects` や `full_audit` の設定）はコメントとして残します。**監視停止 ＋ SACL も削除** で監視フォルダを外すと元に戻ります。include したファイルやレジストリで定義した共有は変更しません
- 監査は共有への新しい接続から始まります。すでに接続しているクライアントは、接続し直したあとから記録されます
- パスは大文字と小文字を区別します。ユーザー名は Samba が記録する名前（ドメイン参加時は `DOMAIN\user`）で、接続元の端末名は SMB の接続から取ります
- 読み取り・書き込みは、Windows と同じくファイルを開くときに要求したアクセスで判断します。削除と名前変更は、実際に行われたときに記録します。拒否されたアクセス、権限変更、作成、名前変更後のパスも記録します（[アクセス種別の判定](#アクセス種別の判定accessmask)を参照）。以前のバージョンで設定した共有は、失敗と権限変更の監査を有効にするために **SACL 再適用**（同じボタン）を 1 回押してください。Samba は開くのに失敗したものをすべて記録するため、ジャーナルの増え方が速くなります。避けたい場合は、設定 → 記録ルールの **拒否されたアクセスも記録する** をオフにして再適用してください
- アンインストールは、先に監視サーバーでそのサーバーの監視フォルダを外してから、`sudo dnf remove fileaccessmonitor-agent` または `sudo apt remove fileaccessmonitor-agent` を実行します（`apt purge` では登録と送信待ちの記録も削除します）。tar.gz で導入した場合は、展開したフォルダで `sudo sh install.sh --uninstall` を実行します（データも消す場合は `--purge` を付けます）

### 8. Linux の監視サーバー

監視サーバー（Web GUI、データベース、通知、エージェント用ポート）は Linux でも動きます。エージェントから届いた記録だけを表示することも、動いている Linux 自身の Samba のアクセスを記録することもできます。

必要なもの: systemd が動く x86-64 の Linux（Rocky Linux 9.4 で確認。Ubuntu、Debian、RHEL、AlmaLinux も同じ手順）と、導入時の root 権限

```sh
sudo dnf install ./fileaccessmonitor-server-<バージョン>-1.x86_64.rpm   # RHEL・Rocky・Alma
sudo apt install ./fileaccessmonitor-server_<バージョン>-1_amd64.deb    # Ubuntu・Debian
```

新しく入れた場合は **監視専用** で、ユーザー `fileaccessmonitor` で動きます。動かし方の確認と変更は `fileaccessmonitor-server` コマンドで行います。

```sh
fileaccessmonitor-server                        # モード、ポート、サービスの状態を表示
sudo fileaccessmonitor-server --collect         # このマシンの Samba のアクセスも記録（コレクターのサービスが root で動きます）
sudo fileaccessmonitor-server --monitor-only    # 監視専用に戻す
sudo fileaccessmonitor-server --port 8090       # Web GUI のポート（既定は 8080）
sudo fileaccessmonitor-server --https on|off    # Web GUI の HTTPS（セキュリティの項を参照）
```

パッケージ管理を使わない場合は `FileAccessMonitor-<バージョン>-linux-x64-server.tar.gz` を展開し、`sudo sh install.sh` を実行します（オプション: `--collect`、`--monitor-only`、`--port <番号>`、`--https on|off`）。

- `/opt/fileaccessmonitor` に導入され、systemd のサービス `fileaccessmonitor` として、権限のない専用ユーザー `fileaccessmonitor` で動きます（ログ: `journalctl -u fileaccessmonitor`）。`--collect` を指定すると、systemd のサービス `fileaccessmonitor-collector` が root で動き、このマシンの Samba のアクセスを記録します（ログ: `journalctl -u fileaccessmonitor-collector`）。1.10 以前で `--collect` にしていた場合は、更新時に以前の root 用 drop-in がこのサービスに置き換わります。記録と設定は `/var/lib/fileaccessmonitor` にあり、サービスのアカウントだけが読めます。コレクターの状態は `/var/lib/fileaccessmonitor/collector` にあります（`key.hash` を除き root のみ）。改ざん検知の鍵 `chain.key` と `chain-head.json` もここにあるため、データベースと一緒にバックアップしてください
- `https://<サーバー>:8080` を開き、`admin` でログインします（新規インストールは自己署名証明書の HTTPS で、ブラウザーに警告が一度表示されます）。初期パスワードは `/var/lib/fileaccessmonitor/initial-admin-password.txt` にあります（`sudo cat` で表示）
- ファイアウォールが有効な場合は TCP 8080 と 8443 を開けてください（例: `firewall-cmd --permanent --add-port=8080/tcp --add-port=8443/tcp && firewall-cmd --reload`、`ufw allow 8080/tcp && ufw allow 8443/tcp`）。パッケージはファイアウォールを変更しません
- 更新（新しいパッケージを入れる、または `install.sh` をもう一度実行）では、モードとポートを引き継ぎます
- `--collect` の場合、このマシンはエージェントと同じようにサーバーの一覧に出ます。**設定** タブで監視フォルダを追加すると、[Linux エージェント](#7-linux-のファイルサーバーsamba-エージェント)と同じ方法で監査を設定します。1 台のマシンには、監視サーバーとエージェントのどちらか一方だけを入れます（一方のパッケージを入れると、もう一方は置き換えられます）
- 通知の秘密情報（Webhook の URL、SMTP のパスワード）は `/var/lib/fileaccessmonitor/keys` の鍵で暗号化し、その鍵はフォルダの権限で保護します（Windows では、鍵自体もマシンの DPAPI で暗号化します）
- 削除は `sudo dnf remove fileaccessmonitor-server` または `sudo apt remove fileaccessmonitor-server` です。記録と設定は残ります（`apt purge` では削除します）。tar.gz で導入した場合は、展開したフォルダで `sudo sh install.sh --uninstall` を実行します（`--purge` を付けると記録と設定も削除します）

## セキュリティ

- **権限の分離**: Web GUI・API・データベースは昇格した権限では動作しません（[どのアカウントが何を実行するか](#どのアカウントが何を実行するか)を参照）。権限が必要な処理（Security ログの読み取り、SACL の設定、共有フォルダとアクセス権のスキャン）は、2 つ目のプロセスであるコレクターが行います。コレクターには Web インターフェースも待ち受けポートもありません。両者はエージェント用ポートにループバックアドレスで接続し、コレクターは SYSTEM（root）だけが読めるランダムな秘密情報で自分を証明します。Web GUI 側が持つのはそのハッシュだけです。
- **JWT 署名鍵**: 初回起動時にランダム生成し `C:\ProgramData\FileAccessMonitor\jwt.key`（SYSTEM / Administrators と Web GUI のサービスアカウントのみ読み取り可）に保存します。`appsettings.json` に 32 バイト以上の `Jwt:Key` を設定した場合はそちらを使用します
- **ログイン試行制限**: 同じユーザー名で、同じ接続元アドレスから 15 分以内に 5 回失敗すると、そのアドレスからそのユーザーでのログインを 15 分間止めます。ほかのアドレスからは同じユーザーでログインできるため、他人のアカウントを締め出すことはできません。どのユーザー名でも合わせて 20 回失敗したアドレス、どのアドレスからでも合わせて 100 回失敗したユーザー名も止めます。ループバックからの接続は、アドレスごとには数えません。リバースプロキシの背後では、`ReverseProxy:KnownProxies` にプロキシを登録して、本来の接続元アドレスで数えるようにしてください。回数はメモリーに保持し、サービスを再起動すると数え直します
- **閲覧範囲**: 管理者は **設定 → ユーザー管理** で、Viewer が見られるフォルダを限定できます（例: 部署ごとの共有フォルダ）。そのユーザーには、CSV 出力や未使用ファイルを含め、指定したフォルダ配下の記録だけが表示されます。通知先メールアドレスを指定すると、そのフォルダでのアラートもメールで届きます。Admin は全体を見られます。フォルダを指定していない Viewer には何も表示されません。Viewer に全体を見せる場合は［すべてのフォルダ］を選択します（1.11 より前にフォルダを指定していなかった Viewer は、更新時に一度だけ［すべてのフォルダ］に設定されました）。変更は次の操作から反映されます
- **ログイン状態**: ログインは `Jwt:ExpiresHours`（既定 8 時間。1.11.1 より前は 24 時間）有効です。**ログアウト** すると、そのトークンはサーバー側でも無効になり、コピーされていても使えません（同じユーザーのほかのログインはそのままです）。ユーザーの削除・ロール変更・パスワード変更／リセットを行ったときも、その時点で無効になります
- **操作ログ**: ログイン（失敗を含む）、ユーザー管理、設定変更、CSV 出力、通知の送信を記録し、**設定 → 操作ログ** に表示します（Admin のみ）
- **通知の秘密情報**: Webhook URL と SMTP パスワードは暗号化して保存します（ASP.NET Core Data Protection、鍵はマシンの DPAPI で保護し `C:\ProgramData\FileAccessMonitor\keys\` に保存）
- **改ざん検知**: このプログラム以外で変更、削除、追加された記録を、データフォルダの鍵 `chain.key`（と `chain-head.json`）による検証で検出します。どちらも `fileaccess.db` と一緒にバックアップしてください。1.10 より前の記録は保護されません。古いデータベースを復元すると検出結果として表示され、内容を確認したうえで承認します。サーバーで管理者権限を持ち鍵も扱える人は、チェーンを作り直せます。毎日のアンカー（レポートのメール、ダウンロードしたアンカーファイル、転送されたイベントログ）をサーバーの外に保管しておくと、それを示せます。**設定 → 改ざん検知** で状態を確認できます
- **通信の暗号化**: Web GUI は、これまでと同じポートで HTTPS を自分で提供できます。**新規インストール**ではオンで、サーバーが自己署名証明書を作成します（マシン名、アドレス、`localhost` を含み、足りなくなると作り直します）。ブラウザーには初回のみ警告が出ます。1.9 より前から更新した環境は、切り替えるまで HTTP のままです（Windows のインストーラーが選択肢を出します。サイレントインストールは `/HTTPS=1` または `/HTTPS=0`）。次のコマンドで切り替え、サービスを再起動します。`status` で今の設定を確認できます。

  ```powershell
  # Windows（C:\Program Files\FileAccessMonitor で）
  .\FileAccessMonitor.exe web-https on|off|status
  ```

  ```sh
  # Linux
  sudo fileaccessmonitor-server --https on|off
  ```

  お持ちの証明書を使う場合は PFX ファイルを指定します: `FileAccessMonitor.exe web-https on --pfx cert.pfx --pfx-password <パスワード>`（Linux: `sudo fileaccessmonitor-server --https on --pfx cert.pfx --pfx-password-file pw.txt`）。証明書には秘密鍵が必要で、マシン名と合わない場合は警告を表示します。`--redirect-port 8081` を付けると、HTTP のポートを追加で開き、ブラウザーを HTTPS のポートへ転送します。切り替えると、古い `http://` のブックマークは、転送用ポートを使わない限り開けなくなります。証明書を読み込めない場合は、そのマシン自身（`localhost`）だけで HTTP により起動し（他のインターフェースでは待ち受けません）、そこからサインインして修正できるようにします。理由と対処（`FileAccessMonitor.exe web-https status`、新しい PFX、またはリバースプロキシの背後では `web-https off`）はログに出力し、**設定** にも理由を表示します。この場合、転送用ポートは開きません。**設定** で使用中の証明書を確認でき（読み取り専用）、管理者が HTTP のまま画面を開くと警告が出ます。エージェント用ポート 8443 は別の証明書で、影響を受けません。HSTS ヘッダーは出さないため、自己署名証明書はいつでも受け入れられます。リバースプロキシの背後では HTTPS をオフのままにできます（[docs/https.ja.md](docs/https.ja.md) を参照）
- **ロール**: `Admin`（設定・ユーザー管理可）と `Viewer`（閲覧のみ）

脆弱性を見つけた場合は、公開 Issue ではなく [SECURITY.md](SECURITY.md) の手順（非公開報告）でご連絡ください。

### どのアカウントが何を実行するか

| | Windows | Linux |
|---|---|---|
| Web GUI・API・データベース・通知・エージェント用ポート | サービス `FileAccessMonitor`。仮想サービスアカウント `NT SERVICE\FileAccessMonitor`（パスワードなし、権限なし） | systemd `fileaccessmonitor`、ユーザー `fileaccessmonitor` |
| このサーバーでの記録、監査の設定、フォルダとアクセス権のスキャン（ローカル収集がオンのときのみ） | サービス `FileAccessMonitorCollector`、SYSTEM | systemd `fileaccessmonitor-collector`、root |
| エージェント | サービス `FileAccessMonitor`、SYSTEM（従来どおり） | systemd `fileaccessmonitor-agent`、root |

コレクターは、同じプログラムを引数 `collector` で起動したものです。組み込みのエージェントのように動作し、記録を `https://127.0.0.1:<エージェント用ポート>` に送ります（その証明書はフィンガープリントで信頼します）。監視フォルダと記録ルールは Web サービスから受け取り、Web GUI からの処理（SACL の設定、未使用ファイルのスキャン、アクセス権のスキャン）を実行します。登録は不要です。**設定 → エージェント** には、このサーバーの行（状態のみ）として表示され、コレクターが停止すると、接続が途絶えたエージェントと同様に通知されます。コレクターが動いていない間は GUI にその旨が表示され、記録は作られません（エージェントが停止しているときと同様、その間のイベントは Security ログに残ります）。コレクターの状態はデータフォルダ内の `collector\` にあり、Web サービスからは読めません。

インストールや更新の後、Web サービスが `NT SERVICE\FileAccessMonitor` で動き続けなかった場合、インストーラーは動作を続けられるよう LocalSystem（1.10 と同じ）に戻し、`logs\service-install.log` に警告を書きます。`Get-CimInstance Win32_Service -Filter "Name like 'FileAccessMonitor%'" | Select-Object Name, State, StartName` でアカウントを確認し、`logs\app-*.log`（またはアプリケーションのイベントログ）で原因を調べ、直してからインストーラーをもう一度実行してください。

この分離により、Web 側に欠陥があった場合の影響は小さくなりますが、コレクターに何をさせるかは引き続き Web サービスが決めます。Web サービスのアカウントを乗っ取った人は、監視フォルダを変え、コレクターにフォルダとアクセス権のスキャン（ファイル名・サイズ・ACL。ファイルの内容は含みません）を依頼でき、記録の変更や削除もできます。監視サーバーは保護すべきシステムとして扱ってください。Web GUI には管理用ネットワークからだけ接続できるようにし、更新を続け、改ざん検知のアンカーをサーバーの外に送ってください（[改ざん検知の仕組み](docs/integrity.ja.md)）。推奨する構成は、監視だけを行う監視サーバー（Linux、ユーザー `fileaccessmonitor`）と、ファイルサーバーごとのエージェントです。

## 設定

### appsettings.json（`publish\` 内）

| 設定項目 | 説明 | 既定値 |
|---|---|---|
| `Kestrel.Endpoints.Http.Url` | 待ち受け URL | `http://0.0.0.0:8080` |
| `Jwt:ExpiresHours` | ログインの有効期間（時間） | `8` |
| `Jwt:Key` | JWT 署名鍵（通常は指定不要。上記参照） | 自動生成 |
| `ExcludeSystemAccounts` | SYSTEM やコンピューターアカウント（`xxx$`）のアクセスを除外 | `true` |
| `ExcludeProcessNames` | 除外するプロセス名 | `System`, `svchost.exe`, `SearchIndexer.exe` |

インストーラーで導入した場合、`appsettings.json` は `C:\Program Files\FileAccessMonitor\` にあり、更新時に上書きされます。独自の設定は同じフォルダの `appsettings.Production.json` に書いてください。このファイルはインストーラーが指定ポートで作成し、更新時も内容が保持されます。

### 実行時の設定・データ（`C:\ProgramData\FileAccessMonitor\`）

| ファイル | 内容 |
|---|---|
| `settings.json` | 監視フォルダ・記録するイベント種別・逆引き DNS サーバー・保持期間・通知設定（GUI から変更）、このサーバー自身のアクセスを記録するか（`LocalCollection`）、Web GUI の HTTPS（`Web:Https`。`web-https` が書き込み） |
| `web-https.pfx` / `web-user.pfx` | Web GUI の証明書（自己署名証明書と、`--pfx` で指定した証明書）。1.10 以前の Windows では自己署名証明書をマシンの証明書ストアに保存していました。ストアに残っている証明書は、そのまま使用されます |
| `agent-endpoint.pfx` | エージェント用ポートの証明書（自己署名。エージェントはフィンガープリントで固定します）。1.10 以前がマシンの証明書ストアに作成した証明書もそのまま使用されるため、フィンガープリントは変わりません |
| `fileaccess.db` | アクセス記録（SQLite） |
| `logs\app-YYYYMMDD.log` | Web サービスのアプリケーションログ（14 日保持） |
| `logs\service-install.log` | インストーラーがサービス・アカウント・フォルダのアクセス権に対して行った処理の記録（サービスの登録や起動に失敗したと表示された場合に確認します） |
| `collector\` | コレクターのサービスの状態。SYSTEM と Administrators のみアクセス可（Web サービスは、コレクターの秘密情報のハッシュ `collector\key.hash` だけ読めます）: `key.secret`、`settings.json`（このサーバーの監視フォルダと記録ルールの写し）、`outbox\`、`logs\collector-YYYYMMDD.log` |
| `jwt.key` | JWT 署名鍵 |
| `chain.key` | 改ざん検知の鍵。`fileaccess.db` と一緒にバックアップしてください（なければ古い記録を検証できません） |
| `chain-head.json` | 改ざん検知が最後に確認したチェーンの末尾。`fileaccess.db` と一緒にバックアップしてください |
| `permission-reports\` | 監視フォルダごとの権限スキャンの最新結果（**アクセス権** タブ） |

データフォルダにアクセスできるのは、SYSTEM、Administrators、Web サービスのアカウントだけです（エージェントでは SYSTEM と Administrators）。`ProgramData` のままでは、ローカルのすべてのユーザーが読めてしまうため、インストーラーがこのように設定します。**バックアップも同じように閉じた場所に保管してください**。バックアップには、すべての記録に加え、`chain.key`（改ざん検知の鎖を作り直せる鍵）と `jwt.key`（Admin を含む任意のユーザーとしてサインインした状態を作れる鍵）が含まれます。エクスプローラーや `Copy-Item` でコピーすると、コピー先のアクセス権（たとえば Users が読める `C:\Temp`）になります。`robocopy <データフォルダ> <バックアップ先> /E /COPYALL` でコピーするか、Administrators だけが開けるフォルダにコピーしてください。

| ダッシュボード | アクセス推移グラフ、種別内訳、拒否された試みの件数、上位ファイル／フォルダ。グラフの値をクリックすると、該当する記録（［検索］タブ）またはファイル・フォルダの詳細を表示します |
| ファイル別 / フォルダ別 / ユーザー別 | ランキングと詳細ダイアログ |
| 最新アクセス | アクセスログ（接続元 IP・端末名付き）。拒否された試みは赤い **拒否** の印が付き、「結果」の絞り込みで表示・非表示を切り替えられます。名前変更は移動先も表示し、権限変更は内容を見る情報ボタンがあります。ファイル名の横の時計のボタンで、そのファイルの履歴を表示します |
| 検索 | キーワード・期間・種別・IP による横断検索。結果を CSV で出力（最大 20 万件、Excel で開けます） |
| 未使用ファイル | 監視フォルダ内で、指定期間に読まれていない（アクセスのない）ファイルとその容量を、フォルダを調べて一覧・フォルダ別に集計（Admin のみ、1 回あたり最大 10 万ファイル） |
| アクセス権 | 監視フォルダとその配下の、最後のスキャン時点での権限。単に継承しているだけでない項目、広いアクセス（Everyone、Authenticated Users など）、継承を切っているフォルダを表示します。スキャンは管理者だけが開始できます。フォルダの閲覧範囲を持つ Viewer は、自分のフォルダについて保存済みの結果を見られます |
| 設定 | 監視フォルダ、ユーザー管理、記録ルール（除外・連続した読み取りのまとめ）、逆引き DNS、データ保持期間、通知、定期レポート、改ざん検知、操作ログ |

通知（Teams / Slack / Webhook / メール）は、1 人のユーザーが数分以内に設定件数以上のファイルを削除・書き込み・読み取りしたとき（大量読み取りは既定でオフ）、1 人のユーザーが設定回数以上アクセスを拒否されたとき（**拒否の連続**。既定は 5 分で 20 回）、ランサムウェアに似た動きがあったとき（**緊急**。下記）と、記録が途切れたとき（Security ログのイベントが収集前に上書きされた、またはログが消去された。消去したユーザーも通知。Linux のサーバーでは journald が監査ログを捨てた、またはジャーナルに残っていなかった）に送信します。連絡が途絶えたエージェントも通知します。インターネットへの接続にプロキシが必要な場合は、通知設定でプロキシを指定してください（Webhook のみ。サービスはサービスアカウントで動くため、ログオンしているユーザーの Windows のプロキシ設定は使われません）。

Webhook の宛先には、このマシン自身（localhost、`127.x.x.x`、`::1`）、リンクローカルアドレス（クラウドのメタデータ用アドレスを含む `169.254.x.x` と `fe80::`）、未指定アドレス、マルチキャストアドレスは指定できません。URL の保存時と、接続時の両方で確認するため、名前解決の結果がこれらのアドレスになる場合も拒否されます。リダイレクトには従いません。ネットワーク内のチャットサーバー向けに、プライベートアドレス（`10.x`、`172.16-31.x`、`192.168.x`）は使用できます。

**ランサムウェアに似た動き** は、ユーザーごとに 2 分間の操作を 3 つのルールで見ます。同じ新しい拡張子（`.tmp` のような無害なものを除く）への 20 ファイル以上の名前変更（新しいパスが必要なので、Windows では USN ジャーナルが必要）、100 回以上の書き込みと 50 回以上の名前変更が重なったとき、身代金要求文のようなファイル名（`README_DECRYPT.txt`、`HOW_TO_RECOVER_FILES.html` など）が 3 つ以上のフォルダに作られたときです。この通知は優先度を高くして送り（「【緊急】」の印。メールは重要度高）、該当したルールとファイルを示します。自動で何かを止めたり切断したりはしません。既定でオンで、通知設定でオフにできます。数値は `settings.json` の `Alerts` にあります。通知は、他の通知と同じく有効にしたときだけ送ります。

**ファイルの履歴。** ファイル名の横の時計のボタン（最新アクセス、検索結果、ファイル別の一覧、ファイルとフォルダの詳細ダイアログ）を押すと、そのファイルやフォルダの履歴を表示します。今の場所に至るまでと、その後の出来事を、名前変更と移動をたどって示します。フォルダの名前変更と移動もたどりますが、名前変更は「削除」の種類と一緒に記録されるため、そのフォルダで **削除** を監視している必要があります。閲覧範囲の外の手順は隠し、「閲覧範囲の外」の区切りとして表示します。CSV で出力できます。

**アクセス権のレポート。** **アクセス権** タブで、監視フォルダとその配下について、最後のスキャン時点の権限を表示します。単に継承しているだけでない項目、広いアクセス（SID で判定するため、Windows の表示言語に関係ありません）、継承を切っているフォルダを示します。スキャンは管理者が **今すぐスキャン** で開始します。Linux では POSIX の権限と Samba の共有の設定（`guest ok`、`read only`、`valid users`、`write list`）も表示します。`acl_xattr` または `acl_tdb` を使う共有の NT ACL は読まず、その旨を警告します。既定ではフォルダだけを調べます（ファイルは通常フォルダの権限を引き継ぐため）。ファイルも調べるときは **フォルダのみ** のチェックを外します。スキャンには上限があり（既定は 5,000 フォルダ、50,000 ファイル、結果は 20,000 行まで）、上限で止まった場合はその旨を表示します。その場合は、各フォルダの横のボタンでサブフォルダをスキャンするか、［対象フォルダ］に監視フォルダの下のフォルダを入力して［今すぐスキャン］を押します。［対象フォルダ］の右のボタンで、監視フォルダとサブフォルダのスキャン結果を選べます。管理者は［削除］でサブフォルダのスキャン結果を削除できます。権限のジョブには 1.10 以降のエージェントが必要です。

**定期レポートのメール。** 既定ではオフです。**設定 → 通知** の **定期レポート** のカードで、毎日・毎週・毎月、サーバーのローカル時刻にメールで概要を送ります。アクセス、拒否された試み、権限変更、よく使われたファイル・フォルダ・ユーザー、保存済みの最新スキャンによる広いアクセスを含みます（レポートはスキャンを開始しません）。管理者には、さらにアラート、エージェントの状態、改ざん検知の状態も届きます。CSV の添付は任意です。通知先メールアドレスを持つ Viewer には、そのフォルダだけを対象にしたレポートが届きます（閲覧範囲の画面で「定期レポート（範囲内のみ）もこのアドレスに送る」を外すと届きません）。先に メールを設定してください。**テストレポートを今すぐ送る** は、スケジュールを変えずに送って確認できます。

**改ざん検知。** 新しいアクセス記録と操作ログの各行は、直前の行と鍵付きのハッシュ（HMAC）でつながります。このプログラム以外で行われた変更、削除、追加、順序の入れ替えは、15 分ごとの検証（毎晩は全件）で見つかり、緊急の通知を送ります。設定の **改ざん検知** のカードで状態を確認し、今すぐ検証、署名付きのアンカーのダウンロード、確認後の承認ができます。毎日、チェーンの末尾を Windows のイベントログ（ソース `FileAccessMonitor`、イベント 1100）または syslog（タグ `fileaccessmonitor`）に書き込み、定期レポートにも含めます。鍵はデータフォルダの `chain.key` で、データベースと一緒にバックアップしてください。1.10 より前に保存された記録は保護されません。仕組みと運用の詳細は [改ざん検知の仕組み](docs/integrity.ja.md) を参照してください。

## 仕組み

1. Windows セキュリティイベントログ（4663 / 4659 / 4660、権限変更の 4670、拒否された操作の失敗 4656）をリアルタイムに購読し、作成と新しい名前は NTFS 変更ジャーナルから取得
2. ログオン（4624）・共有アクセス（5140）イベントと SMB セッション一覧から接続元 IP / 端末名を補完
3. SQLite に記録し、ASP.NET Core の Web API で集計
4. ブラウザ（Bootstrap + Chart.js）で表示

他の Windows ファイルサーバーのエージェントは 1・2 を行い、記録を HTTPS で監視サーバーに送ります。Linux のエージェントは、代わりに Samba の監査ログを systemd のジャーナルから読みます（[7. Linux のファイルサーバー](#7-linux-のファイルサーバーsamba-エージェント)を参照）。

### アクセス種別の判定（AccessMask）

| 種別 | Mask 値 |
|---|---|
| 読み取り (Read) | `0x1` (ReadData) / `0x80000000` (GENERIC_READ) |
| 書き込み (Write) | `0x2` (WriteData) / `0x4` (AppendData) / `0x40000000` (GENERIC_WRITE) |
| 削除 (Delete) | `0x10000` (DELETE) の後に同じハンドルのイベント 4660（オブジェクトの削除）、およびイベント 4659 |
| 名前変更 (Rename) | `0x10000` (DELETE) の後にイベント 4660 がない（名前変更・移動）。新しいパスは、使えれば USN ジャーナルから取得 |
| 作成 (Create) | ファイルを作った書き込み。USN ジャーナルで判定します（[Windows での作成と名前変更](#windows-での作成と名前変更usn-ジャーナル)を参照）。ジャーナルがなければ書き込み |
| 権限変更 (Permission) | イベント 4670（権限・所有者の変更）。所有者、追加・削除されたエントリ、継承の変更内容を記録 |
| 拒否 (Denied) | 独立した種別ではなく、拒否された読み取り・書き込み・削除（監査失敗の 4656）を、その種別の記録に **拒否** の印を付けて残します |

拒否されたアクセスは、ファイルに加えてフォルダ（入れないフォルダを開く・一覧する）も、ユーザー・パス・種別ごとに 60 秒以内のものを 1 件にまとめて記録します。拒否の記録は、ランキング・統計・未使用ファイルの判定や、読み取り・書き込み・削除のアラートではアクセスとして数えません。**設定 → 記録ルール** でオフにできます。Windows では、拒否された名前変更は拒否された削除として記録されます。

Linux（Samba）では、拒否された操作を Samba が失敗した `create_file`（削除・名前変更も同様）として記録します。拒否の判定は、エラーが「Permission denied」「Operation not permitted」の場合に加え、「No such file or directory」でもそのパスが存在する場合に行います（Samba は自分でアクセスを判定するため、古いエラーコードが残るためです）。存在しないパスを開けなかった記録は残しません。作成は「作成のみ」で開かれたときだけ記録し（「作成または開く」で開くクライアントは書き込み）、名前変更は新しいパスを表示し、権限変更（`fset_nt_acl`）は変更前後の内容なしで記録します。

名前変更や移動でもファイルは削除権限で開かれるため、削除権限のアクセスは最大 2 秒保留し、イベント 4660 で実際に削除されたかを判定します。書き込みと名前変更は、その後さらに数秒、USN ジャーナルとの突き合わせのために保留します（上記）。削除されておらず、同じパスにファイルが再び存在する場合（Office は古いファイルを別名に変更し、新しいファイルを元の名前に変更して保存します）は書き込みとして記録します。名前変更は「削除・名前変更」を選択したフォルダで、作成は「書き込み」を選択したフォルダで記録します。

一時的な名前を経由する保存は、Windows でも Linux でも、文書への書き込み 1 件として記録します。除外される名前（`~WRD0001.tmp` など）から記録される名前への名前変更は、変更後の名前への書き込みです。Linux では、文書を除外される名前に変更した直後（5 秒以内）に、別のファイルが元の名前に変更されて入った場合も、同じ保存の一部とみなします（入らなければ名前変更として記録します）。同じユーザーによる同じファイルへの書き込みは、2 秒以内なら 1 件にまとめます（保存では、書き込みのために何度か開くことがよくあるため）。大文字と小文字だけを変えた名前変更は、名前変更として記録します。

フォルダは、削除・名前変更・権限変更されたとき（と、拒否された場合に開こうとしたとき）だけ記録します。画面ではフォルダアイコンで表示し、CSV にもファイルかフォルダかを出力します。ファイル別ランキングと大量削除のアラートには含めません（中のファイルの削除がすでに数えられているため）。フォルダを開いたり、中にファイルを追加したりした操作は記録しません。

### 記録ルール

管理者は **設定** タブで、除外するファイル名のパターン（`*` と `?` が使えます）・ユーザー・プロセスと、連続した読み取りのまとめを設定できます。同じユーザーが同じファイルを前回の読み取りから設定時間内（既定 5 分）に再び読んだ場合は記録しません。時間は読み取りのたびに数え直すため、長い動画をシークしながら見ても 1 回と数えます。既定では `Thumbs.db`、`desktop.ini`、`~$*`（Office のロックファイル）、`*.tmp` を除外します。ルールは保存後に記録するアクセスに適用されます。

## 他のツールとの比較

FileAccessMonitor の目的は、ログ基盤を構築せずに「ファイルサーバーで誰がファイルを読み・変更し・削除したか」を少人数の運用で確認できるようにすることです。それ以上が必要な場合は、他のツールの方が合っている可能性があります。

| | FileAccessMonitor | 商用の監査製品<br>（例: Netwrix Auditor、ManageEngine ADAudit Plus） | Wazuh |
|---|---|---|---|
| 費用 | 無料（MIT） | 有償ライセンス | 無料（OSS）。有償のクラウド版・サポートあり |
| 導入 | ファイルサーバーにインストーラーを 1 つ実行。2 台目以降はエージェントを導入 | インストーラー。別途サーバーやデータベースが必要な場合が多い | Wazuh サーバー・インデクサー・ダッシュボードの構築と、各ホストへのエージェント導入 |
| 対象範囲 | Windows ファイルサーバーと、Samba で共有する Linux ファイルサーバーのファイルアクセス | ファイルサーバー、NAS、Active Directory、Microsoft 365 など | 多数のホストを対象としたセキュリティ監視（SIEM/XDR） |
| 誰がファイルを**読んだ**か | 可（Security ログのイベント 4663/4659。Linux は Samba の監査モジュール） | 可 | ファイル整合性監視は変更のみ。読み取りは Security ログの収集と独自ルールが必要 |
| 複数サーバーの一元表示 | 可（エージェントが 1 台の監視サーバーに送る） | 可 | 可 |
| アラート | 大量削除・変更・読み取り、拒否の連続、ランサムウェアに似た動き（緊急、自動対応なし）と記録の途切れを Teams / Slack / Webhook / メールへ通知 | 多数の組み込みルール | 柔軟なルールと自動対応 |
| 失敗（拒否）したアクセス | 可（**拒否** として記録） | 可 | Security ログの収集と独自ルールが必要 |
| 権限変更 | 可（Windows は内容つき。Linux は変更前後なし） | 可 | Security ログの収集と独自ルールが必要 |
| レポート | 検索と CSV 出力 | コンプライアンス向けレポート、定期レポート | ダッシュボード、コンプライアンス対応表 |
| 日本語 UI | あり | 製品による | なし |
| サポート | コミュニティ（GitHub Issues）、SLA なし | ベンダーサポート | コミュニティ、または有償サポート |

**選び方の目安**

- **FileAccessMonitor**: Windows や Samba のファイルサーバーが 1 台～数台で、「このファイルを消したのは誰か」「このフォルダを誰が開いたか」を確認したい。ログ基盤は運用したくない。
- **商用製品**: ファイルサーバーに加えて NAS 製品や AD、Microsoft 365 をまとめて監査したい、コンプライアンス向けレポートやベンダーサポートが必要。
- **Wazuh**: 組織全体のセキュリティ監視を構築しており、ファイルアクセスはその情報源の 1 つ。

上記の各製品の機能は公開情報に基づく概要であり、変更される可能性があります。詳細は各製品のドキュメントを確認してください。

## 制限事項

- **ファイルを開かない操作は記録されません。** 属性・更新日時の参照のみ（`0x80` ReadAttributes など）やフォルダの一覧表示は対象外です（拒否されたフォルダの一覧表示は記録します）。たとえば差分バックアップツールが「変更なし」と判定してコピーしなかったファイルは記録されません
- サービス停止中（更新や再起動など）に発生したアクセスは、Security ログ（Linux ではジャーナル）に残っていれば次の起動時に記録します。すでに消えていた場合は、欠落したことを操作ログに記録して通知します
- 監視するファイルサーバーごとに FileAccessMonitor（1 台構成またはエージェント）を入れる必要があります。入れられないサーバーや NAS 製品は監視できません
- Linux では、Samba（SMB）の共有経由のアクセスだけを記録します。NFS や、サーバー上での直接の操作は対象外です
- 名前変更・移動は、変更後のパスが分かる場合に記録します。Windows は NTFS の USN ジャーナルから取得し（ジャーナルのないボリューム、FAT、exFAT、ネットワークのパスでは変更前のパスのみ）、Linux は Samba から取得します。監視フォルダの外から中への移動は、元のパスが監視対象外のため記録しません。別のボリュームへの移動は、削除と作成になります
- Windows では、代替データストリーム（`file.txt:stream`）だけへの書き込みは記録しません。Windows はダウンロードしたすべてのファイルにストリーム（`Zone.Identifier`）を付けるため、ストリームは対象外にしています
- Windows の Security ログには実際に使われた権限だけが残るため、空のファイルの作成（エクスプローラーの **新規作成 → テキスト ドキュメント** など）や、上書き用に開いてファイルを空にする操作は、ログに何も残りません。1.11.2 からは、これらを USN ジャーナルから記録します。30 秒以内に、ログに残った書き込みで説明できない作成・書き込みを、ユーザー **(unknown)** で記録します。誰が行ったかまで記録するには、**設定 → 記録 → 空のファイルの作成者も記録する** をオンにします。すべてのファイルを開く操作を監査し（ハンドルの操作の成功。Security ログの量がおよそ 2 倍になるため、ログのサイズを大きくしてください）、そこからユーザー、接続元 IP、端末名を取ります。この設定がオフのときは、サービスやシステム アカウントが書き込まずに作った空のファイルも (unknown) で記録されます。USN ジャーナルのない場所（FAT、exFAT、ネットワークのパス）では、どれも記録されません
- Linux では、Samba はファイルを開くときにクライアントが要求した権限を記録し、実際に何をしたかは記録しません。書き込みは「書き込み用に開いた」という意味です。そのように開いて更新日時や属性だけを変えた場合も書き込みになり、読み書き両用で開いたファイルは書き込みだけが記録されます。Windows は実際に使われた権限を記録します
- 作成は、Windows では USN ジャーナルがあるとき、Linux では「作成のみ」で開かれたときだけ記録し、それ以外は書き込みになります。Windows でファイルをコピーすると（既存のファイルへの上書きや、robocopy が作るフォルダも）、コピー時にセキュリティ情報が設定されるため、コピー先について権限変更が 1 件記録されることがあります。USN ジャーナルがあるときは、この記録に **作成時の設定** と表示し、定期レポートの権限変更には数えません（1.10.2 より前の記録には表示されません）。Windows で拒否された名前変更は、拒否された削除として記録されます
- 改ざん検知は、1.10 より前の記録を保証できず、`chain.key` を持つ管理者を止めることもできません。サーバーの外に保管したアンカーだけが、それを示せます
- 権限レポートは Linux では POSIX の権限を表示し、Samba の NT ACL は読みません（`acl_xattr` または `acl_tdb` を使う共有には警告を出します）。グループはメンバーに展開せず、スキャンはその日時点のものです
- ランサムウェアに似た動きの検知は固定のしきい値（`settings.json` の `Alerts`）で、自動対応はしません。時間をかけてゆっくり暗号化されると検知できず、多数の拡張子を変える一括移動などは誤検知になることがあります。Linux の拒否の検知は Samba のエラー文言と言語に依存します（英語と日本語の文言に対応）
- 削除・名前変更されたフォルダは、処理時点でまだ存在するか、直前に中のファイルへのアクセスがあった場合にフォルダと判定します。それ以外（空のフォルダなど）はファイルとして記録されます
- 時刻は UTC で保存し、画面ではブラウザのタイムゾーンで表示・日別集計します

## 開発

```powershell
dotnet build FileAccessMonitor.csproj
dotnet test tests/FileAccessMonitor.Tests
dotnet test linux-agent/tests            # Linux エージェント（Windows 上でも実行できます）
```

Linux エージェントは `linux-agent/` のプロジェクトで、エージェントの通信・送信待ち・記録ルールを Windows のサービスと共有しています（ソースファイルをリンク）。`dotnet publish linux-agent/FileAccessMonitor.Agent.Linux.csproj -c Release -r linux-x64 --self-contained true /p:PublishSingleFile=true` でビルドします。監視サーバーの Linux 版はメインのプロジェクトから `dotnet publish FileAccessMonitor.csproj -c Release -r linux-x64 --self-contained true /p:PublishSingleFile=true /p:InvariantGlobalization=true /p:PredefinedCulturesOnly=false` でビルドします（`linux-server/` のインストーラーと一緒に配布）。

インストーラーを手元で作る場合は、[Inno Setup 6](https://jrsoftware.org/isinfo.php) をインストールしてから `.\build-installer.ps1 -Version 1.0.0` を実行します。`dist\` に出力されます。

開発やデモのために、インストール済みの環境に影響を与えず別のインスタンスを動かす場合は、環境変数 `FILEACCESSMONITOR_DATA` で別のデータフォルダ（既定は `C:\ProgramData\FileAccessMonitor`）を、`$env:Kestrel__Endpoints__Http__Url = 'http://localhost:5099'` などで別のポートを指定します。

GitHub Actions（`.github/workflows/ci.yml`）で push / Pull Request ごとにビルド・テスト・発行を実行します。`v1.0.0` のようなタグを push すると、`.github/workflows/release.yml` がインストーラー、zip 版、Linux エージェントと Linux 監視サーバーの tar.gz を作成し、GitHub Releases に公開します。
## アンインストール

インストーラーで導入した場合は、**設定 → アプリ** から **File Access Monitor** をアンインストールします。サービス（コレクターを含む）とファイアウォール規則は削除されます。アクセス記録・設定・鍵は `C:\ProgramData\FileAccessMonitor\` に残るので、不要であればそのフォルダを削除してください。監査エントリ (SACL) も削除する場合は、アンインストールの前に `C:\Program Files\FileAccessMonitor\scripts\restore-audit.ps1` を実行してください。

ソースから導入した場合:

```powershell
.\install-service.ps1 -Uninstall
.\restore-audit.ps1 -SharePaths "D:\Share"   # 監査設定を元に戻す場合
```

Linux エージェントと Linux の監視サーバーの削除は、[7. Linux のファイルサーバー](#7-linux-のファイルサーバーsamba-エージェント)と[8. Linux の監視サーバー](#8-linux-の監視サーバー)を参照してください。

## ダウンロードしたファイルの検証

リリースのファイルは、このリポジトリの[リリース用ワークフロー](.github/workflows/release.yml)が GitHub Actions 上でタグ付きのソースからビルドしています。各リリースには GitHub の[ビルド証明（artifact attestation）](https://docs.github.com/ja/actions/security-for-github-actions/using-artifact-attestations)が付いており、ファイルがこのワークフローでビルドされ、改ざんされていないことを確認できます。[GitHub CLI](https://cli.github.com/) で次のように実行してください。

```powershell
gh attestation verify FileAccessMonitor-Setup-<バージョン>.exe -R nuts-i77/FileAccessMonitor
```

GitHub CLI を使わない場合は、`Get-FileHash <ファイル>`（Linux では `sha256sum <ファイル>`）の結果をリリースページの `SHA256SUMS.txt` と照合してください。Linux では、ダウンロードしたフォルダで `sha256sum -c --ignore-missing SHA256SUMS.txt` を実行すると、まとめて照合できます（1.11.2 より前のリリースはファイルの改行が Windows 形式のため、先に `sed -i 's/\r$//' SHA256SUMS.txt` を実行してください）。

## プライバシーポリシー

本プログラムは、利用者またはインストール・運用する人が明示的に指定しない限り、他のネットワーク上のシステムに情報を送信しません。外部に送信するのは、管理者が設定した場合だけです。具体的には、設定タブで指定した Webhook URL・メールサーバーへの通知と、同じく設定タブで指定した DNS サーバーへの接続元 IP アドレスの逆引きです。エージェントは、登録した監視サーバーにアクセス記録を送信します。

更新の確認: 管理者が Web 画面を開いたとき、1 日 1 回まで、管理者のブラウザが GitHub API（`api.github.com`）にこのプロジェクトの最新リリースを問い合わせます。通常の Web アクセスと同様に、ブラウザの IP アドレスとユーザーエージェントが GitHub に伝わります。ファイルサーバーや記録の内容は送信せず、ファイルサーバー自体も外部と通信しません。**設定 → アプリ情報** で無効にできます。
