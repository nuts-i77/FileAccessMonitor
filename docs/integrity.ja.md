# 改ざん検知の仕組み

[English](integrity.md) | 日本語

1.10 以降の FileAccessMonitor は、保存したアクセス記録と操作ログが後から書き換えられていないかを検査します。このページでは、その仕組み、検知できること・できないこと、運用で気を付ける点を説明します。

画面での操作は［設定］→［改ざん検知］で行います。

---

## 1. 概要

- 記録は 1 行ずつ、**直前の行と鍵付きのハッシュでつながった鎖（チェーン）** として保存されます。
- 途中の記録を書き換える、削除する、別の記録を差し込む、のいずれを行っても鎖がつながらなくなり、検証で見つかります。
- ハッシュの計算には、データベースとは別のファイルに保存した **鍵（`chain.key`）** を使います。データベースのファイルだけを手に入れた人は、鎖をつなぎ直すことができません。
- 鎖の末尾の値（**アンカー**）を毎日 Windows イベントログ / syslog とレポートメールに書き出します。サーバーの外に残したアンカーと照合すれば、サーバーの管理者権限を持つ人による作り直しも見つけられます。

対象は次の 2 つで、それぞれ独立した鎖になっています。

| 鎖 | 対象 |
|---|---|
| `access` | アクセス記録（読み取り・書き込み・削除などの記録） |
| `audit` | 操作ログ（設定の変更、ログイン、通知の送信など） |

---

## 2. 記録のつなぎ方

新しい行を保存するとき、FileAccessMonitor は次の値を計算して行に付けます。

```
番号（ChainSeq） = 直前の行の番号 + 1
封印（ChainHash）= HMAC-SHA256( 鍵, 直前の行の封印 + この行の内容 )
```

```
 [行 1]          [行 2]          [行 3]          …   [行 n]  ← 末尾（アンカーに書き出す値）
 番号 1          番号 2          番号 3               番号 n
 封印 h1 ──────▶ 封印 h2 ──────▶ 封印 h3 ──────▶ … ▶ 封印 hn
 (= HMAC(鍵, 起点 + 行1))  (= HMAC(鍵, h1 + 行2))
```

- **行の内容** には、サーバー名、日時、種別、拒否かどうか、フォルダかどうか、ユーザー、パス、ファイル名、フォルダ、接続元 IP・端末名、名前変更先、権限変更の内容が含まれます（操作ログは、日時、ユーザー、操作、詳細、接続元 IP）。どの項目を 1 文字でも変えると、その行の封印が合わなくなります。
- 表示用のラベル「作成時の設定」（1.10.2 以降）は封印の対象外です。
- 番号は 1, 2, 3, … と欠番なく続きます。保存は 1 件ずつ順番に行い、同じ番号は付きません（データベース上でも重複できないようにしています）。
- 鎖の末尾（最後の番号と封印）は、データベースの `ChainHeads` に加えて、データフォルダの `chain-head.json` にも保存します。`chain-head.json` 自体も鍵で保護されています。

### 鍵

| ファイル | 内容 |
|---|---|
| `chain.key` | 32 バイトの乱数。初回の起動時に作られます。SYSTEM、Administrators、Web サービスのアカウント `NT SERVICE\FileAccessMonitor`（Linux ではユーザー `fileaccessmonitor` と root）だけが読めます |
| `chain-head.json` | 最後に確認した鎖の末尾。データベースだけを古い状態に戻されたことを見つけるために使います |

場所は、Windows では `C:\ProgramData\FileAccessMonitor\`、Linux では `/var/lib/fileaccessmonitor/` です。

## 3. 検証

| いつ | 範囲 |
|---|---|
| 15 分ごと | 前回の検証以降に追加された記録（［新しい記録のみ］） |
| 毎日 03:30（サーバーの時刻） | 鎖の起点からすべて（［全件検証］） |
| ［今すぐ検証］を押したとき | 全件 |

検証は 5,000 行ずつに分けて読み込むため、検証中も記録の保存は止まりません。

### 見つかるもの

| 画面の表示 | 意味 | 主な原因 |
|---|---|---|
| 記録の変更 | 行の内容が封印と一致しない | 記録の書き換え |
| 記録の削除 | 番号に欠けがある | 途中の記録の削除 |
| 最新の記録の削除 | 鎖が末尾より手前で終わっている | 最新の記録の削除 |
| チェーン末尾の変更 | 保存された末尾が最後の行と一致しない | 末尾の情報の書き換え |
| データベースが古い | データベースが `chain-head.json` より古い状態 | バックアップからの復元、古いデータベースへの差し替え |
| プログラム外で追加された記録 | 番号のない新しい行がある | データベースへの直接の追加 |
| チェックポイントの変更 | 削除や承認の記録が書き換えられている | 下記「チェックポイント」の改変 |
| 鍵の変更 | `chain.key` が記録に使われた鍵と違う | 鍵ファイルの紛失・差し替え |
| 位置の重複 | 2 行が同じ番号を持つ | データベースの直接操作 |

結果には、該当する番号の範囲、行 ID、前後の正常な記録の日時が表示されるため、「いつからいつの間の記録が影響を受けたか」を確認できます。1 か所の書き換えは 1 件の検出として報告されます（その後のすべての行が異常扱いにはなりません）。

### 検出されたとき

- 画面上部に赤い帯が表示されます（管理者のみ）。
- 通知が有効なら、メール / Webhook に高優先度の通知を送ります。確認（承認）されるまで 24 時間ごとに再通知します。
- 操作ログに `integrity.break` が残ります。

---

## 4. 承認（検出後の対応）

原因を調べて問題がないと判断したら（例: 自分でバックアップから復元した）、検出の横の［承認］を押し、確認した内容をメモに入力します。

- 承認すると、その鎖は**現在の状態から新しく始まり**ます。以後はその時点を起点に検証します。
- 承認した検出は消えずに一覧に残り、誰がいつ承認したか、メモとともに確認できます。操作ログにも `integrity.accept` が残ります。
- 承認は「この時点までの状態を受け入れる」という記録です。改ざんされた記録が元に戻るわけではありません。

---

## 5. 保持期間とチェックポイント

保持期間（［設定］→ データ保持）で古い記録を削除すると、鎖の先頭が欠けます。これを改ざんと区別するため、削除の前に **チェックポイント** を作ります。

- チェックポイントには、どの番号までを削除したか、その時点の封印、削除した件数、日時が入り、鍵で保護されます。チェックポイント同士も鎖になっています。
- 検証は、最新のチェックポイントの次の行から始めます。
- 削除は**記録した順（番号順）**に行います。エージェントから遅れて届いた記録があると、保持期間を過ぎた記録が少し長く残ることがあります（番号の順でしか削除できないため）。
- チェックポイントは、保持期間による削除（`retention`）、承認（`accepted`）、改ざん検知の開始（`genesis`）のときに作られます。

---

## 6. アンカー（サーバーの外に残す控え）

鍵とデータベースの両方を操作できる人（監視サーバーの管理者権限を持つ人）は、記録を書き換えたうえで鎖を最初から作り直すことができます。これを見つけるには、鎖の末尾の値を**サーバーの外**に残しておき、あとで照合します。

アンカーの例:

```
FAM-ANCHOR v1 server=STORAGE chain=access seq=12345 hash=9f2c…(64 桁) time=2026-11-07T15:05:00Z audit-seq=678 audit-hash=1ab4…
```

| 出力先 | いつ | 説明 |
|---|---|---|
| Windows イベントログ（アプリケーション、ソース `FileAccessMonitor`、イベント ID 1100） / Linux の syslog（タグ `fileaccessmonitor`） | 毎日 00:05 | 常に出力します。**ログを別のサーバーに転送している場合に**効果があります |
| 定期レポートのメール（管理者宛て） | レポートの送信時 | 定期レポートを有効にしている場合。メールはサーバーの外に残ります |
| ［アンカーをダウンロード］ | 手動 | 鍵による検証値（MAC）付きのファイル（JSON）を保存し、別の場所に保管します |
| アンカーだけの通知メール / Webhook | 毎日 | 既定はオフ。`settings.json` に `"Integrity": { "AnchorNotify": true }` を書くと有効になります |

### 照合のしかた

［アンカーを照合］の欄に、保管しておいた `FAM-ANCHOR` の行、またはダウンロードしたファイルの内容を貼り付けて［照合］を押します。

| 結果 | 意味 |
|---|---|
| 一致 | その時点の記録は、今のデータベースでも同じです |
| 不一致 | その時点以前の記録が変わっています（鎖が作り直された可能性があります） |
| データベースより新しい | データベースが、アンカーを取った時点より古くなっています（復元や差し替え） |
| 保持期間により削除済み | その番号はすでに保持期間で削除されています。チェックポイントと照合します |

## 7. 守れる範囲と限界

| 攻撃者ができること | 検知 |
|---|---|
| データベースのファイルだけを編集・削除・差し替えできる | **できる**（鍵がないため、鎖をつなぎ直せません） |
| データベースを古いバックアップに戻す | **できる**（`chain-head.json` と比較します） |
| 監視サーバーの管理者権限を持つ、または Web サービスのアカウントを乗っ取った（どちらも鍵を読め、データベースを変更できます） | アンカーを**サーバーの外**に残していれば、照合して**検知できます**。外に残していなければ検知できません |
| 記録される前のイベント（Windows のセキュリティログや Samba のログ）を消す | **対象外**。収集が途切れたことは、従来どおり「記録の欠落」の通知で知らせます |

- 1.10 より前に保存された記録は鎖に含まれず、保護されません。画面に「改ざん検知の開始前（日付）の記録 N 件は保護されていません」と表示されます。これらの記録は保持期間が来ると、従来どおり日付で削除されます。
- 改ざん検知は**見つける**仕組みです。書き換えを防いだり、元に戻したりはしません。元に戻すにはバックアップが必要です。
- 鍵とデータベースは同じ監視サーバーにあります。そのため、この仕組みだけでは「管理者でも変更できない保管」にはなりません。監査証跡として使う場合は、アンカー（できれば元のイベントログ / syslog も）を、**監視サーバーの管理者が書き換えられない別の保管先**（追記専用のログ収集サーバー、SIEM、WORM ストレージ、別の管理者が管理するメールボックスなど）に送ってください。保管先の資格情報を監視サーバーに置かないことも重要です。

---

## 8. 運用上の注意

- **バックアップ**: `fileaccess.db` と一緒に `chain.key` と `chain-head.json` もバックアップしてください。`chain.key` を失うと、それまでの記録を検証できなくなります（「鍵の変更」と表示され、承認して新しく始めることになります）。
- **バックアップからの復元**: データベースを復元すると「データベースが古い」と表示されます。復元が意図したものなら、内容を確認して［承認］してください。
- **イベントログの転送**: アンカーを Windows イベントログ / syslog に書くだけでは、同じサーバーの管理者が消せます。ログ収集サーバーや SIEM に転送するか、定期レポートのメールやダウンロードしたアンカーを別の場所に保管してください。
- **イベントソース**: Windows イベントログのソース `FileAccessMonitor` はサービスが初回に自動で作ります。作れなかった場合はソース「Application」で書き込み、ログに警告を出します。その場合は管理者として一度 `New-EventLog -LogName Application -Source FileAccessMonitor` を実行してください。
- **定期的な照合**: 月に 1 回など、保管しているアンカーを［アンカーを照合］で確認すると、管理者権限による作り直しにも気付けます。
