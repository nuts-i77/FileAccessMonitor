## English

### Highlights

**File history.** Next to a file name in the Recent log and in search results, and in the file and folder detail dialogs, a clock button (**History**) opens the history of that file or folder. It shows how the file came to be where it is (created, or arrived by a rename) and what happened to it since, following renames and moves, including a folder that was renamed or moved above the file (up to 50 steps). The timeline has filters per kind, a CSV export and **Open in Search**. A folder's renames and moves are recorded only when **Delete** is monitored for that folder (a rename is recorded together with the Delete access type); the dialog says so.

**Permissions report.** A new **Permissions** tab shows who may do what in a monitored folder and below it, as of the last scan: entries that are not simply inherited, broad access, and folders that do not inherit their permissions. Admins start a scan with **Scan now**. A Viewer with a folder scope reads the stored scan, limited to their own folders; an unscoped Viewer has no access. Broad access is recognized by SID (Everyone, Authenticated Users, Users, Guests, Anonymous, Network, Interactive, Domain Users and so on), so it works on any Windows language. It is rated **high** when it allows change or delete, and **medium** when it allows reading only. Groups are shown as one entry each; they are not expanded.

On Linux the report shows the owner, group, mode and POSIX ACL of each folder and file, and the Samba settings of every share that holds the folder: `guest ok`, `read only`, `valid users` and `write list`. A writable share that allows guests is rated high. Scans are stored per folder (the latest one only). CSV export gives one line per entry. Entries whose permissions were changed after the scan (v1.9 permission records) are marked.

Limits: a scan stops at 5,000 folders, 50,000 files, 8 levels or 5 minutes by default, and at 20,000 rows; the result shows which limit stopped it. Samba NT ACLs of shares that use `acl_xattr` or `acl_tdb` are not read, and the report warns about those shares. While a scan runs, other jobs of that agent wait. The permissions job needs **1.10 agents**: a 1.9 agent is not sent the job, and the GUI asks you to update it.

**Scheduled report e-mail.** Off by default. In **Settings → Notifications**, the **Scheduled report** card sends a summary by e-mail every day, every week (Monday 09:00 by default) or every month (day 1 to 28), at the server's local time. E-mail must be set up first. A report covers the previous day, week or month: accesses by type, refused attempts, permission changes, top files, folders and users, and the broad permissions of the last stored scans. The report never starts a scan. For Admins it also lists alerts sent, the state of the agents and the tamper detection state, with the day's anchor line. CSV attachments (broad permissions, permission changes, refused attempts, top files and users) are optional. Each Viewer with a notification address gets a report limited to their folders, unless **Also send the scheduled report (limited to these folders) to this address** is unticked in the user's scope dialog (ticked by default). Those reports leave out alerts, agents and tamper detection. The webhook option posts a short summary with numbers only. **Send a test report now** sends the last period to the main recipients and does not change the schedule. If the server was down at a scheduled time, the report is still sent when the server is back within 6 hours (daily), 24 hours (weekly) or 48 hours (monthly); otherwise that slot is skipped. A failed send is tried again 3 times, 15 minutes apart.

**Tamper detection.** Each new access record and operation-log entry is linked to the one before it with a keyed hash (HMAC). Records that are changed, deleted, added or reordered outside the program are found by verification, which says where (record numbers and the times around the gap). The chains are checked every 15 minutes, and in full every night at 03:30 local time. A new finding raises a **high priority** alert (when notifications are on) and is repeated every 24 hours until it is accepted. The **Tamper detection** card in Settings shows the state, and a red banner stays on every Admin page until the findings are accepted. Accepting, after you have checked what happened, restarts the chain from its current state; the finding stays in the list.

The secret key is `chain.key` in the data folder, and `chain-head.json` there keeps the last known end of each chain. Back both up together with `fileaccess.db`. Without `chain.key`, the old records cannot be verified (the card then says so).

Every day at 00:05 the end of each chain is also written as a `FAM-ANCHOR` line to the Windows Application event log (source `FileAccessMonitor`, event 1100) or to syslog (tag `fileaccessmonitor`). The same line goes into the scheduled report e-mail. The GUI can download a signed anchor file and check a pasted anchor against the records. An anchor kept off this machine shows that the records were changed, even when someone has administrator rights here. The event log and syslog protect you only when they are forwarded off the machine. Sending each anchor as a notification of its own is off by default; turn it on with `"Integrity": { "AnchorNotify": true }` in `settings.json`.

Retention now deletes records in chain order, so a record older than the retention period can stay a little longer, until the older records before it are deleted. The deletion is recorded, so the chain still verifies.

### Other changes

- New screens: the **Permissions** tab, the **Scheduled report** and **Tamper detection** cards in Settings (Admin), and the per-user checkbox in the viewing-scope dialog.
- Operation log: `permissions.scan`, `permissions.export`, `report.settings`, `report.test`, `report.sent`, `report.skipped`, `integrity.verify`, `integrity.break`, `integrity.accept` and `integrity.anchor`.
- The database gains `ChainSeq` and `ChainHash` on the access-record and operation-log tables, `SendReport` on viewing scopes, and the tables `ChainHeads` and `ChainCheckpoints`. It also gets an index on renamed-to paths for the file history.

### Upgrading

- Windows: run the new installer. Linux: install the new package (or run `install.sh` again). Settings, records and keys are kept.
- **Back up the data folder before upgrading** (`C:\ProgramData\FileAccessMonitor\` on Windows, `/var/lib/fileaccessmonitor` on Linux), including `chain.key` and `chain-head.json`.
- The database is upgraded automatically on the first start. That start can take a little longer on a large database, because the index for the file history is created then.
- Records saved before 1.10 are not protected by tamper detection. The card shows how many there are.
- For the permissions report, **update the agents to 1.10**. Records, file history, the scheduled report and tamper detection work with 1.9 agents as before.
- Nothing needs to change in the audit policy. 1.10 adds no audit setting, and **Re-apply SACL** is not needed for it.
- Restoring an older copy of `fileaccess.db` is reported as a finding (the database is older than it was). Check what happened, then accept it.

### Known limits

- Samba NT ACLs are not shown (warning only). Permissions are shown as POSIX permissions, which can differ from what SMB clients get on such shares.
- Groups are not expanded, and there is no effective-permission calculation per user.
- The scheduled report uses the last stored scan, so the scan can be older than the report (its date is shown).
- File history cannot follow a rename whose destination is unknown (for example on a Windows volume without a USN journal); it shows a gap there.
- Tamper detection cannot prove anything about records saved before 1.10. Someone with administrator rights on the monitoring server who also has `chain.key` can rebuild the chain; only copies of the anchors kept elsewhere show that.
- At most 50 scoped reports are sent per run; the rest are logged and not sent.

## 日本語

### 主な変更

**ファイルの履歴。** 最新アクセスと検索結果のファイル名の横、およびファイル・フォルダの詳細ダイアログに、時計のボタン（**履歴**）を付けました。押すと、そのファイルやフォルダの履歴を表示します。作成されたのか、名前変更で入ってきたのかを含め、今の場所に至るまでと、その後の出来事を、名前変更と移動をたどって示します（上位フォルダの名前変更や移動も含め、最大 50 段階）。種別ごとの絞り込み、CSV の出力、**検索で開く** があります。フォルダの名前変更と移動は、そのフォルダで **削除** が監視対象のときだけ記録されます（名前変更は削除の種類と一緒に記録されるため）。ダイアログにもその旨を表示します。

**アクセス権のレポート。** 新しい **アクセス権** タブで、監視フォルダとその配下について、最後のスキャン時点で誰に何が許可されているかを表示します。単に継承しているだけの項目を除き、広いアクセスと、継承を切っているフォルダを示します。スキャンは管理者が **今すぐスキャン** で開始します。フォルダの閲覧範囲を持つ Viewer は、自分のフォルダに限って保存済みのスキャン結果を見られます。範囲を指定していない Viewer は見られません。広いアクセスは SID で判定するため（Everyone、Authenticated Users、Users、Guests、Anonymous、Network、Interactive、Domain Users など）、Windows の表示言語に関係なく判定します。変更や削除を許すものは「高」、読み取りだけを許すものは「中」とします。グループは 1 件として表示し、メンバーへは展開しません。

Linux では、各フォルダとファイルの所有者、グループ、モード、POSIX ACL と、そのフォルダを含む Samba の共有ごとの設定（`guest ok`、`read only`、`valid users`、`write list`）を表示します。ゲストを許可していて書き込める共有は「高」です。スキャン結果はフォルダごとに最新の 1 回分を保存します。CSV は 1 行 1 件で出力します。スキャン後に権限が変更されたもの（1.9 の権限変更の記録による）には印が付きます。

制限: 既定では 5,000 フォルダ、50,000 ファイル、8 階層、5 分、または 20,000 行で止まります。結果には、どの上限で止まったかを表示します。`acl_xattr` または `acl_tdb` を使う共有の Samba NT ACL は読み取らず、その共有について警告を出します。スキャンの間は、そのエージェントの他のジョブが待ちます。権限のジョブには **1.10 のエージェント** が必要です。1.9 のエージェントには指示を送らず、更新を促すメッセージを表示します。

**定期レポートのメール。** 既定ではオフです。**設定 → 通知** の **定期レポート** のカードで、毎日、毎週（既定は月曜の 09:00）、毎月（1 日から 28 日まで）、サーバーのローカル時刻にメールで概要を送ります。先に「通知」でメール（SMTP サーバーと宛先）を設定してください。レポートは前の日・週・月を対象にします。種別ごとのアクセス、拒否された試み、権限変更、よく使われたファイル・フォルダ・ユーザー、保存済みの最新スキャンによる広いアクセスを含みます。レポートがスキャンを開始することはありません。管理者向けには、送信したアラート、エージェントの状態、改ざん検知の状態と、その日のアンカーの行も含みます。CSV の添付（広いアクセス、権限変更、拒否された試み、よく使われたファイルとユーザー）は任意です。通知先メールアドレスを持つ各 Viewer には、そのフォルダだけを対象にしたレポートが届きます。ただし、ユーザーの閲覧範囲の画面で「定期レポート（範囲内のみ）もこのアドレスに送る」を外した場合は除きます（既定はオン）。この種のレポートには、アラート、エージェント、改ざん検知は含みません。Webhook の項目をオンにすると、数値だけの短い概要を送ります。**テストレポートを今すぐ送る** は、前の期間のレポートを主な宛先だけに送り、スケジュールは変えません。予定の時刻にサーバーが止まっていた場合は、毎日なら 6 時間、毎週なら 24 時間、毎月なら 48 時間以内に起動すれば送信します。それを過ぎた分は送らずに飛ばします。送信に失敗したときは、15 分おきに 3 回まで再送します。

**改ざん検知。** アクセス記録と操作ログの各行は、直前の行と鍵付きのハッシュ（HMAC）でつながります。このプログラム以外で変更、削除、追加、順序の入れ替えが行われた記録は、検証で見つかり、場所（記録の番号と、その前後の時刻）を示します。チェーンは 15 分ごとに確認し、毎晩 03:30（ローカル時刻）にすべてを確認します。新しい検出結果があると（通知をオンにしている場合）緊急の通知を送り、承認されるまで 24 時間ごとに再通知します。設定の **改ざん検知** のカードに状態を表示し、承認されるまで管理者のすべての画面の上部に赤い帯が出ます。内容を確認したうえで承認すると、チェーンは今の状態から再開します。検出結果は一覧に残ります。

秘密の鍵はデータフォルダの `chain.key` で、`chain-head.json` にはチェーンごとに最後に確認した末尾を保存します。この 2 つを `fileaccess.db` と一緒にバックアップしてください。`chain.key` がないと、古い記録は検証できません（カードにもその旨を表示します）。

毎日 00:05 に、各チェーンの末尾を `FAM-ANCHOR` の行として Windows のアプリケーションイベントログ（ソース `FileAccessMonitor`、イベント 1100）または syslog（タグ `fileaccessmonitor`）にも書き込みます。同じ行を定期レポートのメールにも入れます。GUI から署名付きのアンカーファイルをダウンロードでき、貼り付けた行を記録と照合できます。このマシンの外に保管したアンカーがあれば、このマシンで管理者権限を持つ人が記録を変更しても気付けます。イベントログと syslog は、マシンの外に転送している場合にだけ守ります。アンカーを個別の通知として送るのは既定でオフです。`settings.json` に `"Integrity": { "AnchorNotify": true }` を設定するとオンになります。

保持期間の削除は、チェーンの順番で行うようになりました。そのため、保持期間より古い記録が、その前の古い記録が消えるまで少しの間残ることがあります。削除の事実は記録されるので、チェーンは検証できます。

### その他の変更

- 新しい画面: **アクセス権** タブ、設定（管理者）の **定期レポート** と **改ざん検知** のカード、閲覧範囲の画面のユーザーごとのチェックボックス。
- 操作ログ: `permissions.scan`、`permissions.export`、`report.settings`、`report.test`、`report.sent`、`report.skipped`、`integrity.verify`、`integrity.break`、`integrity.accept`、`integrity.anchor` を記録します。
- データベースに、アクセス記録と操作ログの `ChainSeq`、`ChainHash`、閲覧範囲の `SendReport` を追加します。テーブル `ChainHeads` と `ChainCheckpoints` を追加し、ファイル履歴用に名前変更後のパスのインデックスも作ります。

### 更新時の注意

- Windows: 新しいインストーラーを実行してください。Linux: 新しいパッケージを導入してください（または `install.sh` を再度実行）。設定、記録、鍵はそのまま残ります。
- **更新の前にデータフォルダをバックアップしてください**（Windows は `C:\ProgramData\FileAccessMonitor\`、Linux は `/var/lib/fileaccessmonitor`）。`chain.key` と `chain-head.json` も含めてください。
- データベースは初回の起動時に自動で更新されます。データベースが大きいと、ファイル履歴用のインデックスを作るため、初回の起動に少し時間がかかることがあります。
- 1.10 より前に保存された記録は、改ざん検知の保護対象外です。カードに件数を表示します。
- アクセス権のレポートを使うには、**エージェントを 1.10 に更新**してください。ファイル履歴、定期レポート、改ざん検知は、1.9 のエージェントでもこれまでどおり動きます。
- 監査ポリシーは変更する必要はありません。1.10 では新しい監査の設定はなく、**SACL の再適用** も不要です。
- 古い `fileaccess.db` のコピーを戻すと、データベースが以前より古くなったものとして検出結果になります。内容を確認したうえで承認してください。

### 既知の制限

- Samba の NT ACL は表示しません（警告のみ）。POSIX の権限を表示するため、そのような共有では SMB クライアントに適用される内容と異なることがあります。
- グループはメンバーに展開せず、ユーザーごとの実効権限は計算しません。
- 定期レポートは保存済みの最新スキャンを使うため、スキャンがレポートより古いことがあります（スキャンの日時を表示します）。
- 名前変更の移動先が分からない場合（USN ジャーナルのない Windows のボリュームなど）、ファイル履歴はそこで途切れて表示します。
- 1.10 より前に保存された記録は、改ざん検知では保証できません。監視サーバーで管理者権限を持ち、`chain.key` も扱える人は、チェーンを作り直せます。別の場所に保存したアンカーのコピーだけが、それを示せます。
- 閲覧範囲つきのレポートは、1 回の実行で最大 50 件までです。残りは操作ログに記録し、送りません。
