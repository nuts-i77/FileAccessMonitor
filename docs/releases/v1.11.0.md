## English

### Security: the web GUI no longer runs with administrator rights

The web GUI, API and database used to run in the same process as the part that reads the Security log, so a flaw in the web part would have given an attacker SYSTEM (root on Linux). They are now two processes:

| | Windows | Linux |
|---|---|---|
| Web GUI, API, database | service `FileAccessMonitor` as the virtual account `NT SERVICE\FileAccessMonitor` (no password, no privileges) | `fileaccessmonitor` as user `fileaccessmonitor` (also with `--collect`; the root drop-in is gone) |
| Recording on this server, auditing set-up, folder and permission scans | new service `FileAccessMonitorCollector` ("File Access Monitor Collector") as SYSTEM | new service `fileaccessmonitor-collector` as root |

- The collector exists only while the server records accesses on itself (not for "Monitoring server only"). It is the same program started as `FileAccessMonitor collector` and works like a built-in agent: it reports to the web service over loopback on the agent port and needs no registration. It proves itself with a random secret that only SYSTEM (root) can read; the web service holds only the secret's hash (`collector\key.hash`). It is not listed as an agent, but **Settings → Agents** shows its status for this server, and a stopped collector is notified like an offline agent.
- The collector's state (secret, outbox, position, log) is in `collector\` in the data folder, which the web service cannot read. Records are saved under the same server name as before, so existing records, history and settings continue as they were. The agent port also accepts the collector when agents are turned off (on loopback only).
- Setting SACLs, the Unused Files scan and the permission scan of this server's folders are now done by the collector, so the web service no longer needs to read the shares. If the collector is stopped, the GUI says so.
- Certificates: the web service cannot use a key that SYSTEM put in the machine store, so new self-signed certificates are PFX files in the data folder. Certificates made by earlier versions stay in use (the installer lets the web service account read their keys), so **the agent port's fingerprint does not change** and no agent has to register again.
- The web service's secrets in the data folder (`jwt.key`, `chain.key`, `chain-head.json`, certificates, the initial password) can now also be read by the web service account. The event log source `FileAccessMonitor` for the daily anchor is created by the installer.
- Windows **agents** still run as one service as SYSTEM.

### Other security changes

- **Web GUI when the HTTPS certificate cannot be loaded**: if HTTPS is on but the certificate cannot be loaded (for example the PFX file is gone or its password no longer matches), the web GUI is no longer served over plain HTTP on all interfaces. It listens on the machine itself only (`localhost`), so an administrator there can still sign in and fix it, and nothing is sent in clear text over the network. The log tells the reason and how to fix it (`FileAccessMonitor.exe web-https status`, a new PFX, or `web-https off` behind a reverse proxy), and **Settings** shows the reason. The HTTP redirect port stays closed in that case. With HTTPS off (reverse-proxy setups) nothing changes.
- **Viewers without folders see nothing**: until now a Viewer with no folders assigned saw everything. Now a Viewer sees only the assigned folders, and seeing everything needs the explicit **All folders** choice in the user's scope dialog. A new Viewer starts with no folders (the dialog says the user sees nothing until folders are chosen), and removing the last folder no longer turns into "everything". Admins are unaffected. **On upgrade, every existing Viewer without folders is set to All folders once, so what they see does not change**; review them in the Users tab and assign folders where needed.
- **Webhook destinations are restricted**: the notification webhook cannot point to this machine (`localhost`, `127.x.x.x`, `::1`), to link-local addresses (`169.254.x.x`, which includes the cloud metadata address, and `fe80::`), or to unspecified or multicast addresses. This is checked when the settings are saved and again when the connection is made (a name that resolves to such an address is refused), and redirects are no longer followed. Private addresses (`10.x`, `172.16-31.x`, `192.168.x`) stay allowed for chat servers inside the network.
- **The data folder is no longer readable by Users** (Windows): it used to inherit read access for all local users from `ProgramData`, so anyone who could sign in to the server could read `fileaccess.db`. The installer now limits it to SYSTEM, Administrators and the web service account (on an agent: SYSTEM and Administrators).

### Improvements

- **A full agent outbox no longer drops records**: when the outbox reaches 2 GB, the agent pauses collection and checks every 30 seconds for room, instead of dropping new records. The records stay in the Security log (Linux: the journal) and are collected once the monitoring server is reachable again, as long as the log has not wrapped first (then the existing recording-gap notice applies). The agent reports this in its heartbeat; the **Agents** tab shows **Send queue full** and a notification is sent once. Older agents and servers keep working together (the new field is optional).
- **Web GUI files are revalidated on every load**: after an update, browsers sometimes kept an old `app.js`. Pages, scripts and styles are now sent with `Cache-Control: no-cache`, so the browser always asks whether they changed (a 304 answer when they did not). Fonts, images and the bundled libraries stay cacheable.

### Upgrading

- Monitoring server and agents (the agent outbox change is in the agent). A 1.10.x agent keeps working with a 1.11.0 server and the other way round; an old agent simply does not report a full outbox.
- The database is migrated at the first start: the Users scope gets an **All folders** flag (existing Viewers without folders are converted once), and the Agents table gets two columns for the outbox state.
- Run the new installer (Windows) or install the new package / run `install.sh` (Linux). Existing installs are switched automatically: the services are re-registered with the new accounts, the data folder's permissions are updated (this can take a moment with a large data folder), the collector service is created and started, and the Security log is read from where the old service stopped. On Linux the former root drop-in is replaced with the collector service.
- Updating by copying files (`deploy-remote.ps1`) does not switch an install from 1.10: run the installer once.
- If you start the collector by hand, run it elevated: `FileAccessMonitor.exe collector`. `local-collection on|off` only changes the setting; the installer (or `sc.exe config FileAccessMonitorCollector start= auto|disabled`, `fileaccessmonitor-server --collect|--monitor-only`) enables or disables the service.

## 日本語

### セキュリティ: Web GUI を管理者権限で動かさないようにしました

これまでは、Web GUI・API・データベースが、Security ログを読む部分と同じプロセスで動いていたため、Web 側の欠陥から SYSTEM（Linux では root）の権限を奪われるおそれがありました。今回から、次の 2 つのプロセスに分けています。

| | Windows | Linux |
|---|---|---|
| Web GUI・API・データベース | サービス `FileAccessMonitor`。仮想サービスアカウント `NT SERVICE\FileAccessMonitor`（パスワードなし、権限なし）で動作 | `fileaccessmonitor`。ユーザー `fileaccessmonitor` で動作（`--collect` でも同じです。root 用の drop-in はなくなりました） |
| このサーバーでの記録、監査の設定、フォルダとアクセス権のスキャン | 新しいサービス `FileAccessMonitorCollector`（「File Access Monitor Collector」）。SYSTEM で動作 | 新しいサービス `fileaccessmonitor-collector`。root で動作 |

- コレクターは、このサーバー自身のアクセスを記録する場合にだけ存在します（［監視サーバーのみ］では存在しません）。同じプログラムを `FileAccessMonitor collector` として起動したもので、組み込みのエージェントのように動作します。Web サービスにはエージェント用ポートへのループバック接続で報告し、登録は不要です。SYSTEM（root）だけが読めるランダムな秘密情報で自分を証明し、Web サービスはその秘密情報のハッシュ（`collector\key.hash`）だけを持ちます。エージェントの一覧には含まれませんが、［設定］>［エージェント］にこのサーバーの状態が表示され、コレクターが停止すると、接続が途絶えたエージェントと同様に通知されます。
- コレクターの状態（秘密情報、送信待ち、読み取り位置、ログ）は、データフォルダ内の `collector\` にあり、Web サービスからは読めません。記録はこれまでと同じサーバー名で保存されるため、既存の記録・履歴・設定はそのまま引き継がれます。エージェント機能を無効にしている場合も、エージェント用ポートはコレクターのためにループバックだけで待ち受けます。
- このサーバーの SACL の設定、未使用ファイルのスキャン、アクセス権のスキャンはコレクターが行うため、Web サービスが共有フォルダを読める必要はなくなりました。コレクターが停止している間は、GUI にその旨が表示されます。
- 証明書: Web サービスは SYSTEM がマシンのストアに作った鍵を使えないため、新しい自己署名証明書はデータフォルダ内の PFX ファイルとして作成します。以前のバージョンが作成した証明書はそのまま使用されます（インストーラーが Web サービスのアカウントにその鍵の読み取りを許可します）。そのため、**エージェント用ポートのフィンガープリントは変わらず**、エージェントの再登録は不要です。
- データフォルダ内の Web サービスの秘密情報（`jwt.key`、`chain.key`、`chain-head.json`、証明書、初期パスワード）は、Web サービスのアカウントも読めるようになりました。日次のアンカー用のイベントログのソース `FileAccessMonitor` は、インストーラーが作成します。
- Windows の**エージェント**は、これまでどおり 1 つのサービスとして SYSTEM で動作します。

### その他のセキュリティの変更

- **HTTPS の証明書を読み込めない場合の Web GUI**: HTTPS がオンでも証明書を読み込めない場合（PFX ファイルがない、パスワードが合わないなど）に、Web GUI をすべてのインターフェースで暗号化されない HTTP により提供することをやめました。そのマシン自身（`localhost`）だけで待ち受けるため、そのマシン上の管理者がサインインして修正でき、ネットワーク上に平文で流れることもありません。ログに理由と対処（`FileAccessMonitor.exe web-https status`、新しい PFX、リバースプロキシの背後では `web-https off`）を出力し、［設定］にも理由を表示します。この場合、HTTP の転送用ポートは開きません。HTTPS をオフにしている場合（リバースプロキシ構成）は、動作は変わりません。
- **フォルダ未指定の Viewer には何も表示しません**: これまで、フォルダを指定していない Viewer にはすべてが表示されていました。今後は、指定したフォルダだけが表示され、すべてを表示するには、ユーザーの閲覧範囲の画面で明示的に［すべてのフォルダ］を選択する必要があります。新しい Viewer はフォルダなしで作成され（フォルダを指定するまで何も表示されない旨が画面に表示されます）、最後のフォルダを削除しても「すべて表示」にはなりません。Admin への影響はありません。**更新時に、フォルダ未指定の既存の Viewer は、一度だけ［すべてのフォルダ］に変換されるため、見える範囲は変わりません**。［ユーザー］タブで確認し、必要に応じてフォルダを指定してください。
- **Webhook の宛先を制限**: 通知用の Webhook の宛先には、このマシン自身（`localhost`、`127.x.x.x`、`::1`）、リンクローカルアドレス（クラウドのメタデータ用アドレスを含む `169.254.x.x` と `fe80::`）、未指定アドレス、マルチキャストアドレスは指定できません。設定の保存時と接続時の両方で確認し（名前解決の結果がこれらのアドレスになる場合も拒否します）、リダイレクトには従いません。ネットワーク内のチャットサーバー向けに、プライベートアドレス（`10.x`、`172.16-31.x`、`192.168.x`）は引き続き使用できます。
- **データフォルダを一般ユーザーから読めないようにしました**（Windows）: これまでは `ProgramData` から「Users が読み取り可」を引き継いでいたため、サーバーにサインインできる人は誰でも `fileaccess.db` を読めました。インストーラーが、SYSTEM・Administrators・Web サービスのアカウント（エージェントでは SYSTEM と Administrators）だけに限定します。

### 改善

- **エージェントの送信待ちが満杯になっても記録を破棄しません**: 送信待ちが 2 GB に達すると、エージェントは新しい記録を破棄せず、収集を一時停止して 30 秒ごとに空きを確認します。記録は Security ログ（Linux ではジャーナル）に残り、監視サーバーに再び接続できた後に収集されます（それまでにログが上書きされた場合は、既存の記録中断の通知が送信されます）。この状態はハートビートで報告され、［エージェント］タブに［送信待ちが満杯］と表示され、通知が 1 回送信されます。古いエージェントや古いサーバーとも引き続き連携できます（新しい項目は省略可能です）。
- **Web GUI のファイルを毎回確認するようにしました**: 更新後に、ブラウザーが古い `app.js` を使い続けることがありました。ページ、スクリプト、スタイルシートを `Cache-Control: no-cache` で送信し、ブラウザーが毎回変更の有無を確認するようにしました（変更がなければ 304 の応答です）。フォント、画像、同梱のライブラリは、従来どおりキャッシュされます。

### 更新時の注意

- 監視サーバーとエージェントの両方を更新してください（送信待ちの変更はエージェント側にあります）。1.10.x のエージェントは 1.11.0 のサーバーと、その逆の組み合わせでも動作します。古いエージェントは、送信待ちの満杯を報告しないだけです。
- データベースは初回起動時に移行されます。ユーザーの閲覧範囲に［すべてのフォルダ］の項目が追加され（フォルダ未指定の既存の Viewer は一度だけ変換されます）、エージェントのテーブルに送信待ちの状態を保持する 2 つの列が追加されます。
- Windows は新しいインストーラーを実行し、Linux は新しいパッケージを入れる（または `install.sh` を実行する）だけです。既存の環境は自動で切り替わります。サービスを新しいアカウントで登録し直し、データフォルダの権限を更新し（データフォルダが大きい場合は少し時間がかかります）、コレクターのサービスを作成して起動し、Security ログは古いサービスが止まった位置から読み続けます。Linux では、以前の root 用 drop-in がコレクターのサービスに置き換わります。
- ファイルのコピーによる更新（`deploy-remote.ps1`）では、1.10 の環境は切り替わりません。一度インストーラーを実行してください。
- コレクターを手で起動する場合は、管理者として `FileAccessMonitor.exe collector` を実行します。`local-collection on|off` は設定を変えるだけです。サービスの有効化・無効化は、インストーラー（または `sc.exe config FileAccessMonitorCollector start= auto|disabled`、`fileaccessmonitor-server --collect|--monitor-only`）で行います。
