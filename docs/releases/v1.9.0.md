## English

### Highlights

**Refused access is recorded.** An attempt to read, write or delete a file that was refused for lack of permission is now a record of its own, marked **Denied**. Denied records appear in the access log (with a filter), the CSV export and a dashboard counter, but they are not counted as accesses in rankings, statistics or unused-file detection. Repeated attempts by one user on one file within a minute are recorded once. Turn it off under **Settings → Recording**.

**Permission changes are recorded.** A new access type, **Permission**, records who changed the permissions or owner of a file or folder. On Windows the record shows what changed (owner, added and removed entries, inheritance). On Linux (Samba) it shows that the permissions were changed, without before/after details. Tick the new **Permission changes** box for each monitored folder; new folders have it on, existing folders keep their current choice until you tick it.

**Alerts for ransomware-like behaviour.** Three rules watch each user's activity within 2 minutes: many files renamed to the same new extension, a burst of writes together with many renames, and a ransom-note file name (such as `README_DECRYPT.txt`) created in several folders. These alerts are sent with high priority (a "[HIGH PRIORITY]" mark in mail, Slack and Teams). There is no automatic action: nothing is blocked or disconnected. A new alert for a burst of denied attempts (default 20 in 5 minutes) is added as well. Alerts must be turned on, as before.

**Create and the new path of renames.** A file created by an access is now recorded as **Create** instead of Write, and a rename or move shows where the file went.

- Windows: this uses the NTFS change journal (USN journal) of the volume. FileAccessMonitor does not create the journal. A volume without one (and FAT, exFAT or network paths) keeps the old behaviour: Write, and Rename with the old path only. The service log says so once per volume. To check or enable it, see "Create and renames on Windows" in the README (`fsutil usn queryjournal D:`, `fsutil usn createjournal m=33554432 a=8388608 D:`). Records are saved a few seconds later than before, because the journal is matched first.
- Linux: Samba's audit log gives the new path of renames. Create is recorded only when the client opened the file as create-only; clients that "create or open" a file are still recorded as Write.

**HTTPS for the web GUI, on by default for new installs.** A new install serves the web GUI over HTTPS on the same port, with a self-signed certificate it creates (covering the machine name, its addresses and `localhost`). Browsers warn about it once. You can use your own certificate (PFX) instead. Existing installs stay on HTTP until you switch.

```powershell
# Windows (elevated PowerShell in C:\Program Files\FileAccessMonitor), then restart the service
.\FileAccessMonitor.exe web-https on                                   # self-signed certificate
.\FileAccessMonitor.exe web-https on --pfx cert.pfx --pfx-password <password>
.\FileAccessMonitor.exe web-https on --redirect-port 8081              # optional: HTTP port that redirects to HTTPS
.\FileAccessMonitor.exe web-https off
.\FileAccessMonitor.exe web-https status
```

```sh
# Linux
sudo fileaccessmonitor-server --https on                               # (or off)
sudo fileaccessmonitor-server --https on --pfx cert.pfx --pfx-password-file pw.txt
sudo fileaccessmonitor-server --https on --redirect-port 8081
```

The Windows installer has a new option for it (default on for a new install, off when upgrading from before 1.9; silent installs: `/HTTPS=1` or `/HTTPS=0`). After switching, old `http://` bookmarks stop working; the optional redirect port sends them to HTTPS. If the certificate cannot be loaded, the web GUI starts on HTTP and the log says why. The agent port (8443) and its certificate are unchanged. **Settings** has a read-only card, "Web GUI connection (HTTPS)", with the certificate (name, fingerprint, expiry). An Admin who opens the GUI over plain HTTP sees a warning.

### Other changes

- A Viewer limited to some folders no longer sees the destination of a rename or move when it is outside those folders.
- Re-applying SACLs skips folders the service cannot open, instead of failing the whole run; local job errors are reported as messages.
- The monitored-folder list shows which folders need **Re-apply SACL** to get the new auditing (see below).
- Agent protocol: a 1.8 agent works with a 1.9 monitoring server. A 1.9 agent that talks to a 1.8 server sends records without the new data (denied and permission records are not sent, Create is sent as Write, no new paths); the queued records are not rewritten, so they are delivered in full once the server is upgraded.
- The database gains the columns `Denied`, `NewPath` and `Detail` (added automatically at start; no action needed).

### Upgrading

- Windows: run the new installer. Existing installs keep HTTP unless you choose HTTPS.
- **Press "Re-apply SACL" once for each monitored folder** (Windows), or the same button (**Re-apply SACL**) for each folder on a Linux share, to get denied and permission auditing. Until then those records are not produced; reads, writes and deletes continue as before. The Settings page shows which folders still need it.
- On Windows, re-applying (or the service start) also turns on more audit policies: **Handle Manipulation** (failure only; needed to see refused opens: on Windows 11 no refused-open event 4656 is logged without it; `setup-audit.ps1` sets it and `restore-audit.ps1` clears it), **File System** (success and failure) and **Authorization Policy Change** (success, for permission changes). If your organization sets the audit policy by group policy, set these there. The audit entries now also cover changing permissions and taking ownership.
- Linux denied detection relies on Samba's audit log, which logs a refused open of an existing file as "No such file or directory" in many cases (Samba checks access itself and leaves an old error code behind). A failed open of a path that does not exist is not recorded; one of a path that does exist is recorded as Denied. Linux auditing is rewritten by **Re-apply SACL**, which adds the failure and permission operations. Samba logs every failed open, so journal volume may grow; turn off "Also record refused access" and re-apply to remove it.
- Linux agents and servers from 1.8 keep working as described above; upgrade them to get the new data.
- New monitored-folder defaults: new folders have **Permission changes** on. Existing ones do not until you tick it.

### Known limits

- Copying a file on Windows can record one Permission change for the new file, because Windows sets its security while copying.
- Linux records Create only when the file was opened as create-only. Permission changes on Linux have no before/after details.
- Windows records a refused rename as a refused Delete (the two cannot be told apart).
- Create and new paths need the USN journal and are matched to records a few seconds later; moves into a monitored folder from outside it are not recorded (no old path), and moves between volumes are a Delete plus a Create.
- Ransomware-like detection uses fixed thresholds; a slow encryption below the window is not detected, and a bulk move that changes many extensions can raise a false alert. The thresholds other than on/off are in `settings.json` (`Alerts`).

## 日本語

### 主な変更

**アクセスの拒否も記録します。** 権限がなくて拒否された読取・書込・削除の試みを、**拒否** の印を付けた記録として残します。拒否の記録は、アクセスログ（絞り込みあり）、CSV、ダッシュボードの件数に出ますが、ランキングや統計、未使用ファイルの判定ではアクセスとして数えません。同じユーザーが同じファイルに 1 分以内に繰り返した試みは 1 件にまとめます。**設定 → 記録ルール** でオフにできます。

**権限の変更も記録します。** 新しいアクセス種別 **権限変更（Permission）** で、ファイルやフォルダの権限・所有者を誰が変えたかを記録します。Windows では変更内容（所有者、追加・削除されたエントリ、継承）も表示します。Linux（Samba）では権限を変更したことだけで、変更前後の内容は残りません。監視フォルダごとに、新しい **権限の変更** のチェックを入れてください。新しく追加するフォルダは最初から入っており、既存のフォルダは入れるまで今の設定のままです。

**ランサムウェアのような挙動を通知します。** 各ユーザーの 2 分間の操作を 3 つのルールで見ます。同じ新しい拡張子への大量の名前変更、大量の書込と大量の名前変更が重なったとき、身代金要求文のようなファイル名（`README_DECRYPT.txt` など）が複数のフォルダに作られたときです。通知は優先度を高くして送ります（メール・Slack・Teams に「【緊急】」が付きます）。自動で何かを止めたり切断したりはしません。あわせて、拒否が短時間に続いたときの通知（既定は 5 分で 20 回）も追加しました。通知は、これまでどおり有効にしたときだけ送ります。

**作成と、名前変更後のパスを記録します。** アクセスによって作られたファイルは、書込ではなく **作成（Create）** として記録し、名前変更・移動では移動先も表示します。

- Windows: ボリュームの NTFS 変更ジャーナル（USN ジャーナル）を使います。FileAccessMonitor はジャーナルを作りません。ジャーナルのないボリューム（および FAT、exFAT、ネットワークのパス）は、これまでと同じ動作（書込、名前変更は変更前のパスのみ）です。その旨はボリュームごとに 1 回サービスのログに出ます。確認と有効化の方法は README の「Windows での作成と名前変更」を参照してください（`fsutil usn queryjournal D:`、`fsutil usn createjournal m=33554432 a=8388608 D:`）。ジャーナルとの突き合わせのため、記録の保存はこれまでより数秒遅れます
- Linux: Samba の監査ログから名前変更後のパスが分かります。作成として記録するのは、クライアントが「作成のみ」でファイルを開いたときだけです。「作成または開く」で開くクライアントは、これまでどおり書込になります

**新規インストールでは Web GUI が HTTPS になります。** 新しく入れた環境は、同じポートで HTTPS を提供します。証明書は自己署名で、自動作成します（マシン名、アドレス、`localhost` を含みます）。ブラウザーには初回のみ警告が出ます。お持ちの証明書（PFX）を使うこともできます。既存の環境は、切り替えるまで HTTP のままです。

```powershell
# Windows（C:\Program Files\FileAccessMonitor で管理者 PowerShell）。実行後にサービスを再起動
.\FileAccessMonitor.exe web-https on                                   # 自己署名証明書
.\FileAccessMonitor.exe web-https on --pfx cert.pfx --pfx-password <パスワード>
.\FileAccessMonitor.exe web-https on --redirect-port 8081              # 任意: HTTPS へ転送する HTTP ポート
.\FileAccessMonitor.exe web-https off
.\FileAccessMonitor.exe web-https status
```

```sh
# Linux
sudo fileaccessmonitor-server --https on                               # （または off）
sudo fileaccessmonitor-server --https on --pfx cert.pfx --pfx-password-file pw.txt
sudo fileaccessmonitor-server --https on --redirect-port 8081
```

Windows のインストーラーにも選択肢を追加しました（新規は既定でオン、1.9 より前からの更新は既定でオフ。サイレントインストールは `/HTTPS=1` または `/HTTPS=0`）。切り替えると、古い `http://` のブックマークは使えなくなります。転送用ポートを指定すると、そこから HTTPS に転送します。証明書を読み込めない場合は HTTP で起動し、理由をログに出します。エージェント用ポート（8443）とその証明書は変わりません。**設定** の「Web GUI の接続（HTTPS）」（読み取り専用）で証明書（名前、指紋、有効期限）を確認できます。管理者が HTTP のまま画面を開いているときは警告を出します。

### その他の変更

- フォルダを限定した Viewer には、名前変更・移動の移動先がそのフォルダの外にある場合、移動先を表示しません。
- SACL の再適用で、サービスが開けないフォルダがあっても全体を失敗にせず、そのフォルダを飛ばして続けます。ローカルのジョブのエラーはメッセージとして表示します。
- 監視フォルダの一覧に、新しい監査を有効にするために **SACL の再適用** が必要なフォルダを表示します（下記）。
- エージェントの通信: 1.8 のエージェントは 1.9 の監視サーバーとそのまま使えます。1.9 のエージェントから 1.8 のサーバーに送るときは、新しい情報なしで送ります（拒否と権限変更の記録は送らず、作成は書込として送り、新しいパスは付けません）。送信待ちの記録は書き換えないため、サーバーを更新すれば完全な内容で届きます。
- データベースに `Denied`、`NewPath`、`Detail` の列を追加します（起動時に自動。操作は不要です）。

### 更新時の注意

- Windows: 新しいインストーラーを実行してください。HTTPS を選ばない限り、既存の環境は HTTP のままです。
- **監視フォルダごとに「SACL の再適用」を 1 回押してください**（Windows）。Linux の共有でも同じボタン（**SACL の再適用**）を押します。拒否と権限変更の監査は、これで有効になります。それまでこれらの記録は作られませんが、読取・書込・削除はこれまでどおり記録されます。まだ必要なフォルダは設定画面に表示されます。
- Windows では、再適用（またはサービスの起動）で次の監査ポリシーも有効にします。**ハンドル操作**（失敗のみ。拒否された操作を見るのに必要で、Windows 11 ではこれがないと拒否されたオープンのイベント 4656 が記録されません。`setup-audit.ps1` が有効にし、`restore-audit.ps1` が無効に戻します）、**ファイル システム**（成功と失敗）、**承認ポリシーの変更**（成功。権限変更用）です。グループポリシーで監査ポリシーを管理している場合は、そちらで設定してください。監査エントリも、権限の変更と所有権の取得を含むようになります。
- Linux で拒否を見つける仕組みは Samba の監査ログに頼っています。Samba は自分でアクセスを判定するため、存在するファイルを開けなかったときも、古いエラーコードが残って「No such file or directory」と記録されることが多くあります。存在しないパスを開けなかった記録は残さず、存在するパスの場合は拒否として記録します。Linux の監査設定は **SACL の再適用** で書き換わり、失敗と権限変更の操作が加わります。Samba は開くのに失敗したものをすべて記録するため、ジャーナルの量が増えることがあります。増やしたくない場合は「拒否されたアクセスも記録する」をオフにして再適用してください。
- 1.8 の Linux エージェント・サーバーも上記のとおり使えます。新しい情報を得るには更新してください。
- 監視フォルダの既定: 新しいフォルダは **権限の変更** がオンです。既存のフォルダは、入れるまでオンになりません。

### 既知の制限

- Windows でファイルをコピーすると、新しいファイルについて権限変更が 1 件記録されることがあります（コピー時に Windows がセキュリティ情報を設定するため）。
- Linux で作成として記録するのは、「作成のみ」で開かれたときだけです。Linux の権限変更には変更前後の内容がありません。
- Windows では、拒否された名前変更は拒否された削除として記録します（両者を区別できないため）。
- 作成と新しいパスは USN ジャーナルが必要で、記録との突き合わせのため数秒遅れて保存されます。監視フォルダの外から中への移動は記録しません（元のパスが対象外のため）。ボリュームをまたぐ移動は、削除と作成になります。
- ランサムウェアのような挙動の検知は固定のしきい値です。時間をかけてゆっくり暗号化されると検知できず、多数の拡張子を変える一括移動などは誤検知になることがあります。オン/オフ以外のしきい値は `settings.json` の `Alerts` にあります。
